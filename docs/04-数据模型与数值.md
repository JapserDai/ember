# 04 · 数据模型与数值

> 本册前半部分是 **v0.1 要真正实现的 5 张表**，可以直接照着建库。
> 后半部分是完整设计（v0.4+ 才用到），现在**只看不写**。
> 数值表与 `02` 的三档难度表必须逐项一致。
>
> **实现进度**：到 schema v14 为止，库里一共 9 张表——v0.1 的 5 张（`tasks` / `checkins` / `player` / `settings` / `goals`），
> 加上 `streak_bridges`（D38）、`reviews`、`month_reviews`、`journal_entries`（D49）。
> 后四张都记在 §9 的迁移里，不在 §2 的建表 SQL 中——§2 是**已发布的 v1 常量**，按 D31 不许改。

## 0. 三条不可破坏的规则

1. **业务日一律用 `local_date TEXT`（`YYYY-MM-DD`）**，由「本地时间 + dayStart」推导。UTC 毫秒只用于审计与排序。
2. **奖励在写入时固化到行内**。以后调数值，不改历史记录。
3. **随机不参与任何数值计算**。随机只决定文案和动画，所以撤销重记没有经济收益。

## 第一部分：v0.1 的 5 张表

## 1. 为什么是这 5 张

v0.1 只做：任务 + 打卡 + XP/等级 + 五维 + 目标 + 导出。

这六件事需要的事实只有五类：

| 表 | 存什么 | 为什么不能合并 |
| --- | --- | --- |
| `tasks` | 你要做的事 | 长期存在，会被修改、归档 |
| `checkins` | 你做过的每一次记录 | 只追加，是 XP 的唯一来源，永不修改 |
| `player` | 你的等级、属性、余烬 | 单行快照，可随时由 checkins 重建 |
| `settings` | 日界、难度、主题 | 单行配置 |
| `goals` | 一句话目标 | 建表放在 v0.1，界面的列表 / 新建 / 详情在阶段 1 就接上了（进度现算，不存字段）；复盘联动留到阶段 3 |

**关键设计**：`checkins` 是**事实表**，`player` 是**快照表**。快照永远可以从事实重建，所以即使 player 数据坏了也不会丢历史。

## 2. 建表 SQL

```sql
-- ============================================================
-- 打开数据库时必须执行的 PRAGMA
-- ============================================================
PRAGMA journal_mode = WAL;      -- 读写并发更好，崩溃恢复更稳
PRAGMA foreign_keys = ON;       -- SQLite 默认关闭，每个连接都要开
PRAGMA synchronous = NORMAL;    -- WAL 下兼顾安全与性能
PRAGMA busy_timeout = 5000;     -- 写锁最多等 5 秒


-- ============================================================
-- 表 1：player —— 玩家快照（永远只有 1 行）
-- 这一行可以从 checkins 完全重建，坏了也不丢历史
-- ============================================================
CREATE TABLE IF NOT EXISTS player (
  id            TEXT PRIMARY KEY NOT NULL,   -- UUID，同时用作随机种子的一部分
  display_name  TEXT NOT NULL DEFAULT '旅人',

  -- 等级与经验
  level         INTEGER NOT NULL DEFAULT 1
                  CHECK (level BETWEEN 1 AND 50),
  xp_total      INTEGER NOT NULL DEFAULT 0
                  CHECK (xp_total >= 0),      -- 历史累计 XP
  xp_in_level   INTEGER NOT NULL DEFAULT 0
                  CHECK (xp_in_level >= 0),   -- 当前等级内的进度
  highest_level INTEGER NOT NULL DEFAULT 1
                  CHECK (highest_level BETWEEN 1 AND 50), -- 历史最高，撤销时不清零

  -- 五维属性：直接放 5 列，避免为 v0.1 多建一张表
  -- 每列存「属性 XP」，满 200 自动转 1 点（见 4.3）
  attr_body_xp    INTEGER NOT NULL DEFAULT 0 CHECK (attr_body_xp   BETWEEN 0 AND 199), -- 体魄
  attr_mind_xp    INTEGER NOT NULL DEFAULT 0 CHECK (attr_mind_xp   BETWEEN 0 AND 199), -- 心智
  attr_order_xp   INTEGER NOT NULL DEFAULT 0 CHECK (attr_order_xp  BETWEEN 0 AND 199), -- 秩序
  attr_spirit_xp  INTEGER NOT NULL DEFAULT 0 CHECK (attr_spirit_xp BETWEEN 0 AND 199), -- 心力
  attr_bond_xp    INTEGER NOT NULL DEFAULT 0 CHECK (attr_bond_xp   BETWEEN 0 AND 199), -- 联结
  attr_body_pts   INTEGER NOT NULL DEFAULT 0 CHECK (attr_body_pts   >= 0),  -- 已获得的属性点
  attr_mind_pts   INTEGER NOT NULL DEFAULT 0 CHECK (attr_mind_pts   >= 0),
  attr_order_pts  INTEGER NOT NULL DEFAULT 0 CHECK (attr_order_pts  >= 0),
  attr_spirit_pts INTEGER NOT NULL DEFAULT 0 CHECK (attr_spirit_pts >= 0),
  attr_bond_pts   INTEGER NOT NULL DEFAULT 0 CHECK (attr_bond_pts   >= 0),

  -- 货币
  ember         INTEGER NOT NULL DEFAULT 0 CHECK (ember >= 0),      -- 余烬（软货币）
  material      INTEGER NOT NULL DEFAULT 0 CHECK (material >= 0),   -- 材料（硬货币，v0.4 才用）

  onboarding_done INTEGER NOT NULL DEFAULT 0 CHECK (onboarding_done IN (0,1)),

  -- 人物资料：名字在上方 display_name；这里是一句自我介绍
  bio           TEXT,        -- 一句自我介绍，NULL = 从来没写过（v4 加）

  -- 头像：七个像素动物挑一个，只存这一个词（v7 加）
  -- 长相本身是 src/domain/avatar.ts 里的常量，不存进库
  avatar_id     TEXT NOT NULL DEFAULT 'fox',

  -- 下面三列从 v7 起是死列（旧版头像用）。按 D31 不删列，但也没人读写。
  -- v6→v7 那条迁移把 avatar_data 整体清空了：那是用户的相册照片 base64，
  -- 而这一版已经不会再画它——留着只是让库与每份备份多背一张死图片。
  avatar_seed   INTEGER NOT NULL DEFAULT 0 CHECK (avatar_seed >= 0),  -- 废弃
  avatar_data   TEXT,        -- 废弃，已清空（旧版：base64 的 256×256 JPEG）
  avatar_updated_at INTEGER NOT NULL DEFAULT 0,  -- 废弃

  created_at    INTEGER NOT NULL,
  updated_at    INTEGER NOT NULL
);


-- ============================================================
-- 表 2：settings —— 设置（永远只有 1 行，id 固定为 'singleton'）
-- ============================================================
CREATE TABLE IF NOT EXISTS settings (
  id               TEXT PRIMARY KEY NOT NULL DEFAULT 'singleton'
                     CHECK (id = 'singleton'),
  player_id        TEXT NOT NULL REFERENCES player(id) ON DELETE CASCADE,

  -- 业务日
  day_start_hour   INTEGER NOT NULL DEFAULT 4
                     CHECK (day_start_hour BETWEEN 0 AND 23),
  last_settled_date TEXT,        -- 上次结算的业务日；首次启动时设为当天
  week_starts_on   INTEGER NOT NULL DEFAULT 1 CHECK (week_starts_on IN (0,1)), -- 1=周一

  -- 难度与外观
  difficulty       TEXT NOT NULL DEFAULT 'easy'
                     CHECK (difficulty IN ('easy','standard','hard')),  -- 默认轻松
  theme_id         TEXT NOT NULL DEFAULT 'furnace'
                     CHECK (theme_id IN ('furnace','nightvoyage','tundra','daybreak')),
  theme_mode       TEXT NOT NULL DEFAULT 'system'
                     CHECK (theme_mode IN ('system','light','dark')),
  reduce_motion    INTEGER NOT NULL DEFAULT 0 CHECK (reduce_motion IN (0,1)),
  haptics_enabled  INTEGER NOT NULL DEFAULT 1 CHECK (haptics_enabled IN (0,1)),

  -- 时钟异常检测
  max_seen_utc     INTEGER NOT NULL DEFAULT 0,   -- 见过的最大时间戳，用于检测回拨
  last_time_zone   TEXT,                          -- 上次记录的时区，变更时重排通知

  created_at       INTEGER NOT NULL,
  updated_at       INTEGER NOT NULL
);


-- ============================================================
-- 表 3：tasks —— 三类任务（习惯 / 待办 / 奖励）
-- 单表 + type 判别键，理由见第 3 节
-- ============================================================
CREATE TABLE IF NOT EXISTS tasks (
  id               TEXT PRIMARY KEY NOT NULL,
  player_id        TEXT NOT NULL REFERENCES player(id) ON DELETE CASCADE,

  title            TEXT NOT NULL CHECK (length(trim(title)) BETWEEN 1 AND 80),
  notes            TEXT,

  -- 类型
  type             TEXT NOT NULL CHECK (type IN ('habit','todo','reward')),

  -- 重复规则
  recurrence       TEXT NOT NULL CHECK (recurrence IN (
                     'daily',        -- 每天
                     'weekly_days',  -- 每周固定几天
                     'monthly_days', -- 每月固定几号
                     'every_x_days', -- 每 N 天
                     'weekly_times', -- 每周 N 次（灵活）
                     'once'          -- 一次性（待办/奖励）
                   )),
  recurrence_config TEXT NOT NULL DEFAULT '{}',   -- JSON，见 3.3
  anchor_date      TEXT,      -- every_x_days 的锚点业务日
  interval_n       INTEGER CHECK (interval_n IS NULL OR interval_n BETWEEN 1 AND 365),
  weekly_target    INTEGER CHECK (weekly_target IS NULL OR weekly_target BETWEEN 1 AND 7),

  start_date       TEXT NOT NULL,   -- 生效业务日
  end_date         TEXT,            -- 结束业务日（含）
  due_date         TEXT,            -- 待办截止日

  status           TEXT NOT NULL DEFAULT 'active'
                     CHECK (status IN ('active','paused','done','archived')),
  completed_at     INTEGER,         -- 待办完成时间（毫秒）

  -- 五维属性归属
  attribute        TEXT NOT NULL
                     CHECK (attribute IN ('body','mind','order','spirit','bond')),

  -- 显示
  icon             TEXT,
  color            TEXT,
  sort_order       INTEGER NOT NULL DEFAULT 0,

  -- 打卡控制
  max_per_day      INTEGER NOT NULL DEFAULT 1 CHECK (max_per_day BETWEEN 1 AND 10),
  allow_backfill   INTEGER NOT NULL DEFAULT 1 CHECK (allow_backfill IN (0,1)),

  -- 奖励类专用
  ember_cost       INTEGER NOT NULL DEFAULT 0 CHECK (ember_cost >= 0),

  -- 关联目标（可选）。一个任务最多属于一个目标
  -- 不加外键约束：goals 表在本表之后创建，且目标删除是软删除，
  -- 由 repo 层在删除目标时把关联任务的 goal_id 置空，比外键更可控
  goal_id          TEXT,

  created_at       INTEGER NOT NULL,
  updated_at       INTEGER NOT NULL,
  deleted_at       INTEGER,        -- 软删除：NULL = 未删除

  -- 类型与重复规则必须自洽：习惯不能用 once，待办/奖励必须是 once
  CHECK (
    (type = 'habit' AND recurrence IN ('daily','weekly_days','monthly_days','every_x_days','weekly_times'))
    OR (type IN ('todo','reward') AND recurrence = 'once')
  ),
  -- weekly_times 必须给 weekly_target
  CHECK (recurrence <> 'weekly_times' OR weekly_target IS NOT NULL),
  -- every_x_days 必须给 interval_n 与 anchor_date
  CHECK (recurrence <> 'every_x_days' OR (interval_n IS NOT NULL AND anchor_date IS NOT NULL))
);

CREATE INDEX IF NOT EXISTS idx_tasks_player_status
  ON tasks (player_id, status, type) WHERE deleted_at IS NULL;
CREATE INDEX IF NOT EXISTS idx_tasks_due
  ON tasks (player_id, due_date) WHERE deleted_at IS NULL;


-- ============================================================
-- 表 4：checkins —— 打卡事实表（只追加，是 XP 的唯一来源）
-- 每一次记录一行，永不修改，撤销用 status='reversed' 标记
-- ============================================================
CREATE TABLE IF NOT EXISTS checkins (
  id             TEXT PRIMARY KEY NOT NULL,
  player_id      TEXT NOT NULL REFERENCES player(id) ON DELETE CASCADE,
  task_id        TEXT NOT NULL REFERENCES tasks(id) ON DELETE RESTRICT,

  -- 业务日
  local_date     TEXT NOT NULL
                   CHECK (local_date GLOB '[0-9][0-9][0-9][0-9]-[0-9][0-9]-[0-9][0-9]'),
  score_count    INTEGER NOT NULL DEFAULT 0 CHECK (score_count >= 0),  -- 同日第几次（0 基）
  occurred_at    INTEGER NOT NULL,     -- 真实发生时间（毫秒），只用于排序

  source         TEXT NOT NULL DEFAULT 'manual'
                   CHECK (source IN ('manual','backfill','import')),
  status         TEXT NOT NULL DEFAULT 'active'
                   CHECK (status IN ('active','reversed')),

  -- 奖励明细：写入时固化，以后调数值不改历史
  base_xp        INTEGER NOT NULL CHECK (base_xp >= 0),
  xp_awarded     INTEGER NOT NULL CHECK (xp_awarded >= 0),
  base_ember     INTEGER NOT NULL CHECK (base_ember >= 0),
  ember_awarded  INTEGER NOT NULL CHECK (ember_awarded >= 0),
  attr_key       TEXT NOT NULL
                   CHECK (attr_key IN ('body','mind','order','spirit','bond')),
  attr_xp_awarded INTEGER NOT NULL CHECK (attr_xp_awarded >= 0),
  multiplier     REAL NOT NULL CHECK (multiplier >= 0),  -- 难度 × 补记比例
  is_capped      INTEGER NOT NULL DEFAULT 0 CHECK (is_capped IN (0,1)),

  -- 随机（只影响文案与动画，不影响数值）
  prng_seed      TEXT NOT NULL,
  flavor_key     TEXT,

  reversed_at    INTEGER,
  reverse_reason TEXT,

  created_at     INTEGER NOT NULL,
  updated_at     INTEGER NOT NULL,

  -- 同一任务同一天的第 N 次唯一
  UNIQUE (task_id, local_date, score_count)
);

-- 同一任务同一业务日只能有一条有效记录（撤销后可重记）
CREATE UNIQUE INDEX IF NOT EXISTS uq_checkin_active
  ON checkins (task_id, local_date)
  WHERE status = 'active';

CREATE INDEX IF NOT EXISTS idx_checkins_player_date
  ON checkins (player_id, local_date, status);
CREATE INDEX IF NOT EXISTS idx_checkins_task_date
  ON checkins (task_id, local_date, status);


-- ============================================================
-- 表 5：goals —— 目标（列表 / 新建 / 详情在阶段 1 已接；复盘联动到阶段 3）
-- 一句话目标 + 可选截止日。没有子目标、没有阶段、没有百分比。
-- 进度不存字段，每次由「关联任务完成了几个 / 一共几个」现算。
-- ============================================================
CREATE TABLE IF NOT EXISTS goals (
  id            TEXT PRIMARY KEY NOT NULL,
  player_id     TEXT NOT NULL REFERENCES player(id) ON DELETE CASCADE,

  title         TEXT NOT NULL CHECK (length(trim(title)) BETWEEN 1 AND 80),
  why           TEXT,                 -- 为什么想走这一段（可选）
  due_date      TEXT,                 -- 不填就是不限期，不显示倒计时

  status        TEXT NOT NULL DEFAULT 'active'
                  CHECK (status IN ('active','done','archived')),
  completed_at  INTEGER,

  sort_order    INTEGER NOT NULL DEFAULT 0,
  created_at    INTEGER NOT NULL,
  updated_at    INTEGER NOT NULL,
  deleted_at    INTEGER,

  CHECK (due_date IS NULL
         OR due_date GLOB '[0-9][0-9][0-9][0-9]-[0-9][0-9]-[0-9][0-9]')
);

CREATE INDEX IF NOT EXISTS idx_goals_player_status
  ON goals (player_id, status, sort_order) WHERE deleted_at IS NULL;

CREATE INDEX IF NOT EXISTS idx_tasks_goal
  ON tasks (goal_id) WHERE goal_id IS NOT NULL AND deleted_at IS NULL;


-- ============================================================
-- 版本记录（用 SQLite 内置的 user_version，不额外建表）
-- 首次建库后执行：PRAGMA user_version = 2;
-- v1 → v2 见 §9.3：settings 重建（theme_id 加 daybreak）+ player 加 avatar_seed
-- v2 → v3 见 §9.4：player 加 avatar_data（自定义头像）+ avatar_updated_at
-- v6 → v7 见 §9.6：player 加 avatar_id，清空 avatar_data（头像改成七只像素动物）
-- v13 → v14 见 §9.7：新增 journal_entries（日记，D49）
-- v15 → v16 见 §9.8：settings 加 home_prefs（首页偏好，D62）
-- ============================================================
```

## 3. 为什么用单表存三类任务

| 理由 | 说明 |
| --- | --- |
| 共享字段占绝大多数 | 标题、备注、属性、排序、图标、颜色、状态、起止日期、软删除、时间戳，三类完全一致 |
| 「今天」页面要统一查询排序 | 习惯和待办要混排。单表一条 `WHERE` 就行；拆表要 3 次查询 + 内存归并 |
| 打卡外键只能指向一张表 | 拆表后 `checkins.task_id` 就得变成多态外键，SQLite 无法做真外键约束 |
| 加字段只改一处 | SQLite 的 `ALTER TABLE` 能力有限，拆表后每次加字段改 3 张表 |
| 判别键可以用 CHECK 强制约束 | 上面 DDL 里已经保证「习惯不能用 once」这类脏数据进不来 |

**只有约 8 个稀疏列**（`weekly_target / interval_n / ember_cost / due_date` 等），SQLite 存 NULL 的成本极低。

### 3.1 三种类型的行为差异

| | 习惯 habit | 待办 todo | 奖励 reward |
| --- | --- | --- | --- |
| 出现位置 | 每天（按重复规则） | 直到完成 | 奖励区 |
| 完成后 | 明天还会出现 | 从「今天」消失，记录留在历史里 | 消耗余烬 |
| 连胜 | 有 | 无 | 无 |
| 重复规则 | 5 种 | `once` | `once` |
| 奖励 | 产出 XP + 余烬 | 产出 XP + 余烬 | **只消耗** |

### 3.2 重复规则的存储

| 规则 | `recurrence` | 关键字段 / `recurrence_config` |
| --- | --- | --- |
| 每天 | `daily` | 无 |
| 每周一三五 | `weekly_days` | `{"days":[1,3,5]}`，1=周一 |
| 每月 1 号和 15 号 | `monthly_days` | `{"days":[1,15]}` |
| 每 3 天 | `every_x_days` | `interval_n=3, anchor_date='2026-10-01'` |
| 每周 3 次（灵活） | `weekly_times` | `weekly_target=3` |
| 一次性 | `once` | `due_date` 可选 |

**「每周 N 次」不建周进度表。** 进度由 checkins 按业务周聚合得出：

```sql
SELECT COUNT(*) FROM checkins
WHERE task_id = ? AND local_date BETWEEN ? AND ? AND status = 'active';
```

| --- | ---: | ---: |
| 习惯·每日 | 20 | 10 次 |
| 习惯·每周 N 次 | 18 | 12 次（余 16） |
| 待办 | 50 | 4 次 |

属性点上限 99。**无衰减、不清零、不可跨维度使用。**

**状态页怎么读这两个数（D48）**：人升的属性页要显示「这一维的 LV + 一条进度条 + `分数 / 上限`」。Ember 不新增字段，直接把已有的两列重新读一遍：

| 人升要的东西 | Ember 怎么算 | 说明 |
| --- | --- | --- |
| 属性 LV | `points + 1` | 0 点 = 1 级；99 点 = 100 级（与 99 点封顶同一条） |
| 总经验（分数） | `points × 200 + xp` | 就是上面回退公式里的 `total` |
| 进度条 | `xp / 200` | 走满的那一下，正好是「攒够 200、换成 1 点」的那一下 |

**这不是新加的数值**，不参与任何计分（D7）。加属性点仍然只发生在打卡与撤销里（`services/checkin.ts`），状态页只读。

**人生等级的分母是「本级总需」，不是「还差多少」。** 这是两个不同的量，写成同一个会立刻出错：

| 量 | 来源 | Lv.7 本级 900 时 |
| --- | --- | --- |
| 本级总需（显示用分母） | `XP_TABLE[level]` | 915 |
| 还差多少（结算用） | `xpToNextLevel(level, inLevel)` = `915 − 900` | 15 |

第一版拿「还差多少」当分母，于是状态页在差 15 点升级时显示成「900 / 15」、进度条画满，和「我的」页那句「还差 15 到 Lv.8」读起来像两个 App。现在这个换算固定在 `src/domain/status.ts`（`xpLevelTotal()` / `buildStatusView()`），`journal-status-test` 里有一组断言专门盯着它。**不要把这个函数挪回页面里**——页面里有 react-native 与 expo-router，仓库外那套 Node 测试就 import 不到，这组断言也就没地方放。

**撤销时的反向运算**：`regressAttribute(xp, points, loss)`。

属性不是「一条可以往回走的经验条」，而是「点数 + 余数」两个数。撤销一次拿过 20 属性 XP 的记录时，如果当时刚好靠它满了 200 换到 1 点，正确的回退是「点数减 1、XP 变成 180」，而不是「XP 减 20」。所以回退先把「点数 × 200 + XP」还原成总量，扣掉 loss 再拆回去：

```ts
total = points * 200 + xp
take  = clamp(loss, 0, total)      // 先钳到现有总量，扣不成负数
points' = min(99, floor((total - take) / 200))
xp'     = (total - take) % 200
```

点数到 99 之后 `growAttribute` 会丢弃溢出的部分，所以「总量」只是实际存下来的总量，回退结果与之一致，不会出现负值。`growAttribute` 只接受正数 gain，也不能复用——它是「往里加」，不知道点数可以拆回 XP。

```
绝对硬上限 = 3,000 XP / 日
```

## 5. 核心事务：一次打卡

### 5.1 涉及的表与顺序

一次 `scoreTask` 必须在**同一个事务**内完成，否则会出现「打卡成功但没加 XP」。

**落点**：`src/services/checkin.ts`。它不属于 `domain/`（那里是纯函数，不碰数据库），也不属于 `db/repo/`（那里只做单表读写，且仓库之间不许互相 import）。服务层是唯一允许「跨表 + 事务」的地方，分层见 `03` §2。

```
BEGIN TRANSACTION
  1. 校验：任务存在、属于本人、未删除、未暂停
  2. 校验：targetDate 不是未来
  3. 校验：今天这次数 < max_per_day
  4. 校验：补记窗口内（若 source = backfill）
  5. 计算基础奖励（类型 + 难度）
  6. 应用补记折扣（若补记）
  7. 应用每日软上限（读今日已获得量）
  8. 写 checkins 一行（固化所有数值）
  9. 更新 player：xp_total、level、xp_in_level、属性、余烬
 10. 若是待办：更新 tasks.status = 'done'
COMMIT
```

### 5.2 实际实现（`src/services/checkin.ts`）

下面这段就是真实代码的结构，函数名与仓库里一致，可以直接对照读。

```ts
export function scoreTask(input: ScoreTaskInput): ScoreTaskResult {
  return runInTransaction(() => {
    // 1. 设置与业务日。用 effectiveToday：系统时间被调回过去时业务日只能前进
    const settings = getSettings();
    const { today } = effectiveToday(nowMs, settings.day_start_hour, settings.last_settled_date);
    const targetDate = input.targetDate ?? today;

    // 2. 任务
    const task = getTaskById(input.taskId);
    if (!task) return fail('TASK_NOT_FOUND');

    // 3. 排期。weekly_times 要先知道本周做了几次，否则额度用完了还能继续记
    const weeklyDone = task.recurrence === 'weekly_times' ? countInWeek(task, targetDate) : 0;
    if (!isScheduledOn(task, targetDate, settings.week_starts_on, weeklyDone)) {
      return fail('NOT_SCHEDULED');
    }

    // 4. 算分需要的现场。次数按「有效记录」数，撤销后重记才能通过
    const player = getPlayerSnapshot();
    const todayCount = getActiveCheckin(task.id, targetDate) ? 1 : 0;
    const result = computeScore({
      task: toScorable(task), player,
      targetDate, today, nowMs, source,
      difficulty: settings.difficulty, dayStartHour: settings.day_start_hour,
      todayCount,
      todayXp: getDailyXpTotal(targetDate),
      todayEmber: getDailyEmberTotal(targetDate),
    });
    // 被拒绝时事务里一个字都没写，空提交
    if (!result.ok) return { ok: false, code: result.code, message: result.message };

    // 5–7. 写事实行 → 写回玩家快照 → 待办收尾，三件事同生共死
    const checkin = insertCheckinFromDraft(result.checkin);
    updatePlayer({
      xpTotal: result.player.xpTotal, xpInLevel: result.player.xpInLevel,
      level: result.player.level, highestLevel: result.player.highestLevel,
      ember: result.player.ember,
    });
    replaceAttributes(result.player.attributes);
    // D55 起首页不再给待办算分（待办没有完成态），但这一步**保留**：
    // 目标页挂上来的任务、以及导入的旧备份仍可能走到这里
    if (task.type === 'todo') updateTaskStatus(task.id, 'done');

    return { ok: true, checkin, player: getPlayerSnapshot(), awarded: result.awarded,
             levelUp: result.levelUp, cap: result.cap };
  });
}
```

奖励数值的实际计算在 `domain/score.ts` 的 `computeScore()`（纯函数，可单测），
服务层只负责「查现场、调纯函数、落库」。这条分界要守住：
一旦把奖励公式挪进服务层，它就再也没法脱离数据库测试了。

### 5.3 撤销

**允许条件**：该记录所在业务日**尚未结算**，即 `local_date >= last_settled_date`。

```ts
/** 这一天还能不能撤销 */
export function canUndoCheckin(localDate: string, lastSettledDate: string | null): boolean {
  if (!lastSettledDate) return true;
  // 注意 diffDays(a, b) 返回 b - a，方向写反会把该允许的拒掉
  return diffDays(localDate, lastSettledDate) <= 0;
}
```

**撤销必须扣回奖励。** 撤销的语义是「这一次不算数」；如果只把记录标成作废、
奖励留着，每撤销一次就白拿一次 XP 和余烬。

```ts
export function undoCheckin(input: UndoCheckinInput): UndoCheckinResult {
  return runInTransaction(() => {
    // 1. 找到这条事实。已撤销的直接返回 ALREADY_REVERSED（幂等）
    const checkin = /* getCheckinById 或 getActiveCheckin */;
    if (!checkin) return fail('CHECKIN_NOT_FOUND');
    if (checkin.status !== 'active') return fail('ALREADY_REVERSED');

    // 2. 结算保护
    const settings = getSettings();
    if (!canUndoCheckin(checkin.localDate, settings.last_settled_date)) {
      return fail('DAY_ALREADY_SETTLED');
    }

    // 3. 奖励兑换的撤销要退余烬，规则不同；v0.1 界面不产生这类记录，明确拒绝
    const task = getTaskById(checkin.taskId);
    if (task?.type === 'reward') return fail('UNSUPPORTED');

    // 4. 标记事实行（不删除，保留审计）
    reverseCheckin(checkin.id, input.reason ?? null);

    // 5–6. 先算出全部新值，再一次性写回
    const player = getPlayerSnapshot();
    const xpAfter = Math.max(0, player.xpTotal - checkin.xpAwarded);
    const levelBefore = levelFromTotalXp(player.xpTotal).level;
    const levelAfter = levelFromTotalXp(xpAfter);
    const levelsLost = Math.max(0, levelBefore - levelAfter.level);

    // 升级余烬没有写进 checkins 行，必须按「这次撤销掉了几个等级」反推。
    // 少了这一步就留下一条刷余烬的路：打卡升级 +10 → 撤销不回退 → 再打卡再 +10。
    const emberAfter = Math.max(0,
      player.ember - checkin.emberAwarded - levelsLost * LEVEL_UP_EMBER_REWARD);

    // 属性回退：点数可以拆回 XP（见 §4.3 的 regressAttribute）
    const attrs = clone(player.attributes);
    attrs[checkin.attrKey] = regressAttribute(
      attrs[checkin.attrKey].xp, attrs[checkin.attrKey].points, checkin.attrXpAwarded);

    updatePlayer({
      xpTotal: xpAfter,
      xpInLevel: levelAfter.inLevel,
      level: levelAfter.level,
      // 刻意不传 highestLevel：历史最高不该被一次撤销抹掉
      ember: emberAfter,
    });
    replaceAttributes(attrs);

    // 7. 待办重新打开（同 D55 的墓碑：前端已不触发，但旧数据仍会走）。
    // 只在该任务确实因此被关掉、且没有别的有效记录时
    if (task?.type === 'todo' && task.status === 'done' && !getActiveCheckin(task.id, checkin.localDate)) {
      updateTaskStatus(task.id, 'active');
    }

    return { ok: true, checkin: getCheckinById(checkin.id)!, player: getPlayerSnapshot(), losses };
  });
}
```

关键点：

| 点 | 说明 |
| --- | --- |
| 重算顺序 | 先读旧快照，一次算出全部新值再写回。写成「先改 xp_total 再读 player 算等级」会读到改过的值 |
| 等级下降 | 允许。`level` 与 `xp_in_level` 跟着 `xp_total` 重算，`highest_level` 不动 |
| 属性的反向 | 用 `regressAttribute`，不能拿负 gain 去调 `growAttribute`（它只收正数，而且不知道点数能拆回 XP） |
| 升级余烬 | 按 `levelsLost × 10` 扣回，与「撤销后重新打卡会再次发放」严格对称 |
| 幂等 | 已撤销的记录返回 `ALREADY_REVERSED`，不重复扣 |
| 错误码 | `CHECKIN_NOT_FOUND` / `ALREADY_REVERSED` / `DAY_ALREADY_SETTLED` / `UNSUPPORTED`，中文提示统一在 `CHECKIN_ERROR_MESSAGE` 里 |

## 6. 惰性日结算

### 6.1 为什么不后台跑

App 不联网、不做常驻后台。**结算发生在「打开 App 时」**，这叫惰性结算（lazy evaluation）。

好处：即使一周没打开，数据也不会错——打开时补算即可。

### 6.2 结算规则

| 条件 | 行为 |
| --- | --- |
| `last_settled_date` 为空 | 首次启动：设为今天，**不结算任何历史** |
| 今天 < last_settled_date | 时钟回拨：不结算，标记异常，沿用旧值 |
| diff = 0 | 今天已处理：跳过 |
| diff = 1 | 结算昨天 |
| **diff > 1** | **只结算昨天一天**，并记录断签天数（继承 Habitica 的 `multiDaysCountAsOneDay`） |

> **为什么 diff > 1 只结算一天**：断签 10 天和断签 1 天，在习惯养成上的实际影响几乎一样（Lally 2010）。逐日结算只会产生大量无意义的惩罚记录，且用户会觉得被「追着罚」。

### 6.3 实现

- **规则**在 `src/domain/settle.ts` 的 `planSettlement()`：纯函数，不读库不读系统时间，
  输入是 `nowMs / dayStartHour / lastSettledDate / hasRecordOn`，输出是一份结论。
  这样「隔多久只算一天」「回拨不倒退」这些分支能脱离数据库单独验。
- **接线**在 `src/services/settle.ts` 的 `settleUpTo()`：读设置 → 问 domain → 写回。
  写回只有两处：`last_settled_date` 与 `max_seen_utc`。
- **触发**在 `app/_layout.tsx` 的 `bootstrap()`，位置在 `initDatabase()` 之后、
  读设置之前（结算会改写 settings 那一行，先读后结算会读到旧值）。

**`advanceStreak` 没有实现，也不打算实现。** 早先的伪代码里有它（连胜状态机、
宽限券、48h 修复期），按 D21 这些全部取消：连胜从 `checkins` 现算，
事实变了它自己就变，不需要一个状态去维护。v0.2 真要做宽限券与付费修复时，
需要的那几列再单独迁移——不是 §7.1 那一整排。

**结算不惩罚这一条是硬规则**，不是「这一版还没做」：断签只影响连胜数字，
不扣 XP、不掉级、不扣余烬。结算的全部作用是「把撤销的分界线往前推一天」。

下面这段伪代码保留作为设计记录，实现以 `src/domain/settle.ts` 为准：

```ts
export function settleUpTo(nowMs: number): SettleResult {
  return db.withTransactionSync(() => {
    const settings = getSettings();
    const player = getPlayer();
    const rawToday = businessDate(nowMs, settings.dayStartHour);

    // ---------- 时钟回拨保护 ----------
    if (nowMs < settings.maxSeenUtc - 3 * 3_600_000) {
      markClockAnomaly();   // 只标记，不惩罚
    }
    if (nowMs > settings.maxSeenUtc) {
      updateSettings({ maxSeenUtc: nowMs });
    }

    // ---------- 首次启动 ----------
    if (!settings.lastSettledDate) {
      updateSettings({ lastSettledDate: rawToday });
      return { skipped: true, reason: 'first_run' };
    }

    // ---------- 回拨：业务日不倒退 ----------
    if (diffDays(settings.lastSettledDate, rawToday) < 0) {
      return { skipped: true, reason: 'clock_back' };
    }

    // ---------- 同一天 ----------
    if (settings.lastSettledDate === rawToday) {
      return { skipped: true, reason: 'same_day' };
    }

    // ---------- 结算昨天（只结算一天）----------
    const diff = diffDays(settings.lastSettledDate, rawToday);
    const target = addDays(rawToday, -1);

    const hadRecord = countActiveCheckinsOn(target) > 0;

    // 连胜状态机（v0.2 启用；v0.1 只记录 streak 天数）
    const streakResult = advanceStreak({ target, hadRecord, difficulty: settings.difficulty });

    updateSettings({ lastSettledDate: rawToday });

    return {
      skipped: false,
      settledDate: target,
      gapDays: diff - 1,
      hadRecord,
      streak: streakResult,
    };
  });
}
```

- 导入数据完成后
- 前台跨过 dayStart 时（设一个定时器到下一个切换点）

## 7. 连胜状态机

### 7.1 字段（v0.2 已落地：**只加一张桥接表**，见 D38）

**v0.1 不建这些列。** 连胜每次从 `checkins` 现算：`domain/streak.ts` 的
`summarizeDates()` 接收「有记录的业务日」数组，返回 `{ current, best, totalDays, lastDate }`。

为什么：

- 事实表本身就是唯一真相。再加一份计数就有第二份数据要维护，就有对不上的那一天
  （这正是 24 张表方案被砍掉的理由）；
- 撤销一次打卡后，连胜自动回到撤销前的样子，不需要任何补偿逻辑；
- 不加列 = 不加迁移 = 少一次「改 CHECK 要重建表」的风险。

代价：

- 每次首页都要扫一遍历史打卡。按「一个习惯一天一条」算，一年三百多条，
  一次 `SELECT DISTINCT task_id, local_date` + 一次内存分组是毫秒级，**不做缓存**；
- 撤销会删掉事实，所以 `best` 与 `totalDays` 允许随事实**变小**——
  这是「按事实重算」的正确语义，不是 bug（界面也永远不会把它渲染成 0 或「归零」）。

#### v0.2 实际落地：`streak_bridges`（D38）

做修复时面对一个真实矛盾：修复的语义是「这一段空档不算断」，
而空档里**没有 checkin**。只看 checkins 的话，修好的那天算出来还是断的。

所以必须存点东西。但**存的不是连胜**，而是「哪几天算作有记录」：

```sql
-- 迁移 v7→v8（已在 src/db/schema.ts 实现）
CREATE TABLE IF NOT EXISTS streak_bridges (
  local_date     TEXT PRIMARY KEY NOT NULL,   -- 一个业务日只能有一条
  kind           TEXT NOT NULL CHECK (kind IN ('grace','repair')),
  ember_spent    INTEGER NOT NULL DEFAULT 0,
  material_spent INTEGER NOT NULL DEFAULT 0,
  gap_start      TEXT,                         -- 这次修复覆盖的缺口起止（含）
  gap_end        TEXT,
  created_at     INTEGER NOT NULL
);
```

于是 `current` / `best` / `totalDays` 仍然完全由事实算出，只是「事实」从一份变成两份：
真实的打卡 + 被认定有效的日子。撤销打卡照样自动回退，因为那一天的 checkin 没了，
而它本来也不在桥接表里。

**两个关键区别：**

| | 打卡日 | 桥接日 |
| --- | --- | --- |
| 算不算连胜 | 算 | 算 |
| 发不发 XP / 余烬 / 五维 | 发 | **什么都不发** |
| 算不算「累计记录天数」 | 算 | **不算**（那不是「我做过的一天」） |

#### 为什么**不**用下面这排列（原 v0.2 参考，已作废）

存 `streak_current` / `streak_best` 会与事实表重复：撤销一次打卡，
存下来的值不会自己变小，两份数据开始打架。这正是 D21 拒它的理由，
而那个理由**仍然成立**。D38 的结论是：只存推不出来的东西。

### 7.3 规则细节

**v0.1 的实际口径（从 checkins 现算）：**

| 规则 | 实现 |
| --- | --- |
| 什么算「有记录」 | 该业务日至少一条 `status='active'` 的 checkin |
| 今天还没记录 | **不判定为断**。锚点回退到昨天，从昨天往回数（今天还没过完） |
| 今天与昨天都没有记录 | `current = 0`，`best` / `totalDays` 照常保留 |
| 未来日期 | 清洗时丢掉（补记、改设备时间都可能留下这种行） |
| 重复 / 乱序 | `Set` 去重 + 字符串排序（`YYYY-MM-DD` 的字典序就是日期序） |
| 首页每条习惯 | `summarizeStreaks()` 一次分组，不按习惯逐条查库（那才是 N+1） |
| 我的页整体 | 同一份日期数组不分任务，喂 `summarizeDates()` |

下面这些是 v0.2 引入宽限券与修复之后才成立的规则（**已实现**，见 D38）：

| 规则 | 说明 |
| --- | --- |
| 宽限券 | **一券桥接一天**。桥接日不计入 `current` 之外的东西：它算「有记录」，但不发奖励、不计 `totalDays` |
| 宽限券额度 | 轻松 3 / 标准 2 / 硬核 0，每月重置、不累积（`domain/streak.ts` 的 `graceRemaining`） |
| 宽限券时机 | **惰性**：只在 App 打开时补，补的是「昨天」那一天。不打开就不知道断签，也就无从宽恕 |
| 修复 | 一次修复覆盖**整个**断签缺口；恢复值 = 重新现算（把缺口每一天写成 `kind='repair'`） |
| 修复期限 | 最后一个算数日的**业务日结束点 + 48 小时**（`REPAIR_WINDOW_HOURS`）。长期不打开，期限照常流逝 |
| 修复成本 | 轻松 15 余烬 / 标准 40 余烬+1 材料 / 硬核 100 余烬+3 材料 |
| 断签罚款 | **不做**。docs/02 §2.1 表里的 5% / 10% 不实现——与「永不惩罚」冲突，且需要另一套余额审计 |
| 永不降级 | 等级、物品、已写下的日记、称号都不收回 |
| 连胜奖励去重 | 不做（v0.2 没有按连胜发奖） |

### 7.4 展示规则（重要）

断签后界面必须显示：

```
当前连胜：0
历史最佳：23 天
累计记录：147 天
```

**绝不显示「归零」「前功尽弃」。** 这三个数字并排，用户看到的是「我做过很多」，而不是「我失败了」。

## 8. 随机：种子化 PRNG

### 8.1 算法

```ts
/** FNV-1a 32 位哈希：把字符串压成种子 */
export function fnv1a32(input: string): number {
  let h = 0x811c9dc5;
  for (let i = 0; i < input.length; i++) {
    h ^= input.charCodeAt(i);
    h = Math.imul(h, 0x01000193);   // FNV 质数
  }
  return h >>> 0;
}

/** mulberry32：快速、确定、质量足够用于选文案 */
export function mulberry32(seed: number): () => number {
  let a = seed >>> 0;
  return function () {
    a = (a + 0x6d2b79f5) | 0;
    let t = Math.imul(a ^ (a >>> 15), 1 | a);
    t = (t + Math.imul(t ^ (t >>> 7), 61 | t)) ^ t;
    return ((t ^ (t >>> 14)) >>> 0) / 4294967296;
  };
}
```

### 8.2 种子拼接

```ts
// 规则：playerId | localDate | taskId | scoreCount
const seedStr = `${playerId}|${localDate}|${taskId}|${scoreCount}`;

// 每个用途再派生独立流，避免「多抽一次导致后续全变」
const flavorRand = mulberry32(fnv1a32(`${seedStr}|flavor`));
const animRand   = mulberry32(fnv1a32(`${seedStr}|anim`));
```

### 8.3 随机用在哪里

| 用途 | 影响数值？ |
| --- | --- |
| 打卡完成文案 | 否 |
| 探索事件选择 | 否（奖励固定区间，不随机大额） |
| 复盘卡封面图案 | 否 |
| **XP / 余烬 / 材料 / 属性** | **绝不使用随机** |

**这是防「撤销重摇」的根本手段**：随机只影响表现，重摇没有经济收益。

### 8.4 防改系统时间

| 攻击 | 防护 |
| --- | --- |
| 调回昨天重复打卡 | 业务日钳制 + 唯一索引 |
| 调快连续「过」很多天 | diff > 1 只结算一天，无法补领连胜 |
| 调到未来打卡 | `scoreTask` 拒绝未来日期 |
| 改时区绕过 dayStart | 业务日始终用本地时间；`max_seen_utc` 记录异常 |
| 回拨后重领升级奖励 | 升级奖励按等级去重，`highest_level` 保留 |

时钟异常只**标记**，不惩罚、不回滚——避免误伤跨时区旅行的用户。

## 9. 数据迁移

### 9.1 版本管理

用 SQLite 内置的 `PRAGMA user_version`，不额外建表。

```ts
const CURRENT_VERSION = 14;   // 与 src/db/migrate.ts 的 CURRENT_SCHEMA_VERSION 同步

const MIGRATIONS: Array<(db: SQLiteDatabase) => void> = [
  // 索引 0：从 0 升到 1 —— 建所有表
  (db) => { db.execSync(SCHEMA_SQL_V1); },
  // 索引 1：从 1 升到 2 —— 见 §9.3
  (db) => { db.execSync(MIGRATE_V1_TO_V2_SQL); },
  // 索引 2：从 2 升到 3 —— player 加 avatar_data / avatar_updated_at，见 §9.4
  (db) => { db.execSync(MIGRATE_V2_TO_V3_SQL); },
  // 索引 3：从 3 升到 4 —— player 加 bio（一句自我介绍），见 §9.5
  (db) => { db.execSync(MIGRATE_V3_TO_V4_SQL); },
  // 索引 4：从 4 升到 5 —— tasks 加 goal_id
  (db) => { db.execSync(MIGRATE_V4_TO_V5_SQL); },
  // 索引 5：从 5 升到 6 —— tasks 加 reminder_minute
  (db) => { db.execSync(MIGRATE_V5_TO_V6_SQL); },
  // 索引 6：从 6 升到 7 —— player 加 avatar_id，清空 avatar_data，见 §9.6
  (db) => { db.execSync(MIGRATE_V6_TO_V7_SQL); },
  // 索引 7：从 7 升到 8 —— 新增 streak_bridges（连胜宽限券，D38）
  (db) => { db.execSync(MIGRATE_V7_TO_V8_SQL); },
  // 索引 8：从 8 升到 9 —— 新增 reviews（周复盘）
  (db) => { db.execSync(MIGRATE_V8_TO_V9_SQL); },
  // 索引 9：从 9 升到 10 —— 新增 month_reviews（月复盘）
  (db) => { db.execSync(MIGRATE_V9_TO_V10_SQL); },
  // 索引 10：从 10 升到 11 —— player 加 refined_material
  (db) => { db.execSync(MIGRATE_V10_TO_V11_SQL); },
  // 索引 11：从 11 升到 12 —— player 加 last_event_reward_month
  (db) => { db.execSync(MIGRATE_V11_TO_V12_SQL); },
  // 索引 12：从 12 升到 13 —— player 加 guide_start_date（D1–D7 的起算日）
  (db) => { db.execSync(MIGRATE_V12_TO_V13_SQL); },
  // 索引 13：从 13 升到 14 —— 新增 journal_entries（日记，D49），见 §9.7
  (db) => { db.execSync(MIGRATE_V13_TO_V14_SQL); },
];

export function migrate(db: SQLiteDatabase): void {
  const { user_version: current } = db.getFirstSync<{ user_version: number }>(
    'PRAGMA user_version'
  )!;

  // 降级保护：数据库比代码新
  if (current > CURRENT_VERSION) {
    throw new Error('这个数据库来自更新版本的 Ember，请升级 App 后再打开');
  }

  for (let v = current; v < CURRENT_VERSION; v++) {
    MIGRATIONS[v](db);
  }
  db.execSync(`PRAGMA user_version = ${CURRENT_VERSION}`);
}
```

### 9.2 迁移规则

1. **尽量只做加法**：新增列给默认值。改类型、改约束只能重建表（见 §9.3），代价高且要单独验证。
2. **已发布的迁移函数永远不修改**。
3. **每次迁移前复制一份数据库文件**，保留最近 2 份。
4. 导入旧版本 JSON 时，用同样的数组式迁移链处理数据文档，再写库。

### 9.3 唯一的例外：v1 → v2 重建了 settings

v2 做了两件事：

1. `settings.theme_id` 的 CHECK 加上 `'daybreak'`（第四套主题「晨光」）。
2. `player` 加一列 `avatar_seed INTEGER NOT NULL DEFAULT 0 CHECK (avatar_seed >= 0)`。

第 2 件是普通的加法。第 1 件不行：**SQLite 改不了 CHECK 约束**，只能「建新表 → 拷数据 → 删旧表 → 改名」。

为什么宁可重建，也不把 CHECK 去掉：
- `settings` 永远只有 1 行，重建成本可以忽略（一次 INSERT + 一次 DROP）。
- 没有 CHECK 时，`theme_id` 写进非法值，界面会静默回退到炉边，用户会以为「主题设置丢了」。宁可让非法值在写入时直接报错。

迁移 SQL 在 `src/db/schema.ts` 的 `MIGRATE_V1_TO_V2_SQL`，整段跑在迁移器的那一个事务里。要点：

| 要点 | 做法 | 为什么 |
| --- | --- | --- |
| 不用 `SELECT *` | 逐列写死列名 | 列顺序变了也不会错位 |
| 外键 | 新表的 `player_id` 声明与旧表一致 | `PRAGMA foreign_keys = ON` 下，表改名/重建期间外键仍然有效 |
| 索引 | `settings` 本来就没有显式索引，只有主键自带的 autoindex | 重建后自动跟着新表建好，不需要手工补 |
| 幂等 | 不幂等：靠 `user_version` 保证只跑一次 | 迁移链由版本号驱动，不需要每条迁移自己判重 |

### 9.4 v2 → v3：允许上传头像（**已在 v7 废弃**）

> v7 把头像换成了七只像素动物（见 §9.6），这一节描述的两个列 `avatar_data` /
> `avatar_updated_at` 从 v7 起是死列，且 `avatar_data` 已被整体清空。
> 这一节保留是因为「已发布的迁移不能改」——它描述的是历史，不是现状。

v3 只做加法：`player` 加两列。

| 列 | 类型 | 含义 |
| --- | --- | --- |
| `avatar_data` | `TEXT` | 自定义头像：base64 的 256×256 JPEG（**不含** `data:` 前缀）。`NULL` = 没上传过。**v7 起废弃且已清空** |
| `avatar_updated_at` | `INTEGER NOT NULL DEFAULT 0` | 上传时间戳。`0` = 没上传过。只用于显示与备份可读性，不参与任何逻辑 |

**为什么不建新表**：头像与玩家是 1:1，且永远只有一行。单开一张表只会多一次 JOIN，以及一条「这张表什么时候会有第二行」的疑问。

**为什么存 base64 而不是 BLOB**：expo-sqlite 的同步 API 对 BLOB 要绕 `Uint8Array`，base64 字符串是最不容易出错的形式；导出 JSON 时也不用再做一次编码。代价是体积大 33%，但 256×256 的图本来就只有 8–20 KB。

**为什么只存 256×256**：头像最大显示 64px，256 已是 4 倍，导出备份时按 128px 算也够。存原图要处理 4K 与 HEIC，还会让备份膨胀几 MB——而备份是用户要拿去换手机的东西。

老用户升级上来时两列是 `NULL` / `0`，头像仍然是原来那张生成的，不需要任何数据迁移。

### 9.5 v3 → v4：人物资料加一句自我介绍

v4 只做加法：`player` 加一列。

| 列 | 类型 | 含义 |
| --- | --- | --- |
| `bio` | `TEXT` | 一句自我介绍。`NULL` = 从来没写过，`''` = 写过又清空了 |

**为什么加在 `player` 而不是 `settings`**：`settings` 是「把 App 调成你想要的样子」，`player` 是「你是谁、你走到了哪儿」。名字与自我介绍都属于后者。分开放的话，「导出我的资料」要查两张表，而其中一张永远是单行——这种拆法只增加理解成本。

**为什么默认 NULL 而不是 `''`**：`NULL` 表示「从来没写过」，`''` 表示「写过、后来清空了」。这一版界面对两者一视同仁（都不显示那一行），但导出与以后可能的「引导里让新用户写一句」需要区分。

**为什么不加长度 CHECK**：长度上限（80 字）按「用户感知的字数」算，规则在 `src/domain/profile.ts`；SQLite 的 `length()` 算的是码点。两边规则不一致的话，会在边界上出现「界面允许但写库报错」。宁可让长度只在应用层管，也不要在库里放一条规则不同步的约束。

### 9.6 v6 → v7：头像改成七只像素动物

v7 加一列、清一张图。

| 列 | 类型 | 含义 |
| --- | --- | --- |
| `avatar_id` | `TEXT NOT NULL DEFAULT 'fox'` | 挑中的头像 id（`fox` / `cat` / `rabbit` / `panda` / `frog` / `penguin` / `owl`） |

同一迁移里还有一句 `UPDATE player SET avatar_data = NULL, avatar_updated_at = 0`。**这是这个 App 里唯一一条删用户数据的迁移**，所以要写清为什么：

1. `avatar_data` 存的是用户从相册选的那张照片（256×256 JPEG 的 base64，8–20 KB）。这一版头像换成了像素动物，那一列**永远不会再被画出来**——留着它只是让数据库与每一份备份多背一张已经不属于任何东西的图片。用户的要求就是「把现有的头像数据删除」。
2. 它对应的能力（上传自己的照片）已经被产品层面整体移除，不是暂时下线。所以这不是「先删了以后再说」。

**为什么 `avatar_seed` / `avatar_data` / `avatar_updated_at` 三列不删**：按 D31，已发布过的列只能废弃、不能删——删列在 SQLite 里是重建整张表，而 `player` 上有四张表的外键（`settings` / `tasks` / `checkins` / `goals` 都 `REFERENCES player(id)`）。为了三个再也没人读的列去重建一个被四张表引用的表，风险远大于收益。它们从 v7 起是死列，与 `settings.theme_id` 同一种状态。

**为什么 `avatar_id` 不加 CHECK**：加一个七选一的 CHECK 意味着以后每加一只动物都要重建一次 `player` 表。合法性由 `domain/avatar.ts` 的 `normalizeAvatarId` 在读取时兜底：不认识的 id 退回 `fox`，而不是让「我的」页打不开。

**旧备份怎么导入**：备份白名单里那三列仍然保留（旧文件里有它们），`avatar_id` 是新增的白名单列。旧文件没有 `avatar_id` 时，插入走到列默认值 `'fox'`；旧文件带的 `avatar_data` 会被写进去，但 `rebuildPlayerSnapshot` 在导入末尾无条件清空它——否则用户刚删掉的那张照片会从备份里回来，而且是永久地回来。

### 9.7 v13 → v14：新增 `journal_entries`（日记，D49）

```sql
CREATE TABLE IF NOT EXISTS journal_entries (
  local_date  TEXT PRIMARY KEY NOT NULL
                CHECK (local_date GLOB '[0-9][0-9][0-9][0-9]-[0-9][0-9]-[0-9][0-9]'),
  body        TEXT NOT NULL DEFAULT '',
  created_at  INTEGER NOT NULL,
  updated_at  INTEGER NOT NULL
);
```

| 列 | 类型 | 含义 |
| --- | --- | --- |
| `local_date` | `TEXT` 主键 | 业务日（`YYYY-MM-DD`）。**一天只能有一条**，主键就是这个约束本身 |
| `body` | `TEXT NOT NULL DEFAULT ''` | 用户写的那段字。上限 2000 字由 `domain/journal.ts` 管，库里不设 CHECK |
| `created_at` | `INTEGER NOT NULL` | 第一次写这一天的时刻（UTC 毫秒） |
| `updated_at` | `INTEGER NOT NULL` | 最后一次改的时刻 |

**为什么主键是日期而不是自增 id**：日记的语义就是「那一天」。用自增 id 就得再加一条 `UNIQUE(local_date)`，等于把同一个约束写两遍；而「改一句」在这张表里就是 `INSERT OR REPLACE` 同一天那一行，不需要先查 id。

**为什么 `body` 不设长度 CHECK**：同 §9.5 的名字——长度上限按「用户感知的字数」算（`Array.from` 数码点），SQLite 的 `length()` 与它不是一回事。长度只在应用层管，库里不放下一条会不同步的约束。

**为什么 `created_at` 要在改写时保住**：`INSERT OR REPLACE` 会整行换掉。仓库层 `upsertJournalEntry` 先读一次旧的 `created_at` 再写，多一次查询换一个不撒谎的时间戳——「第一次写这一天」的时刻不应该因为改了一句话就变成今天。

**空正文不入库**：保存时正文规范化后为空，服务层直接 `DELETE` 这一天，不写一行空串。理由：空行会让「写过的日子」列表里出现一个点开是空白的条目，而用户以为自己写过。`body` 上的 `DEFAULT ''` 只是为了让插入语句能省略这一列，不是鼓励存空串。

**这一版不存「心情」「天气」「配图」**：日记的定位是「一句话就够」，多一个字段就多一次要填的空。以后要加，按 D31 只能新增列或新表。

**读法有两种，都走主键**（Q9(a)）：
- 日记首页：`listJournalEntries(limit)`，`ORDER BY local_date DESC LIMIT ?`，取最近 60 条。
- 目录页：`listJournalEntriesBefore(beforeDate, limit)`，`WHERE local_date < ? ORDER BY local_date DESC LIMIT ?`。用**日期游标**而不是 `OFFSET`：主键就是日期，条件直接走索引；翻页期间在别处补写了同一天也不会让分页错位（`OFFSET` 会因行数变化跳条）。日期是定长字符串，字典序就是时间序。
- 单日回填：`getJournalEntry(localDate)`。目录页能点到 60 天以外的日子，只靠首页那份视图会找不到。

**备份三处必须同步（铁律二）**：`src/domain/backup.ts` 的 `BACKUP_TABLES`（`sinceSchemaVersion: 14`）、`src/services/backup.ts` 的导出表清单、`src/services/backup-import.ts` 的全量替换 DELETE 列表。漏掉任何一处，日记会在「导出 → 导入」里静默消失。`sinceSchemaVersion` 是必须的：v13 的老备份里没有这张表，没有它旧备份会整份被判为不合法。

### 9.8 v15 → v16：`settings` 加一列 `home_prefs`（D62）

```sql
ALTER TABLE settings ADD COLUMN home_prefs TEXT NOT NULL DEFAULT '{}';
```

| 列 | 类型 | 含义 |
| --- | --- | --- |
| `home_prefs` | `TEXT NOT NULL DEFAULT '{}'` | 一个 JSON 对象，存「首页长什么样」。`'{}'` = 全用代码里的默认值 |

**为什么是一列 JSON 而不是五列。** 这四项（月历 / 火带 / 右滑提示 / 待办条数）没有一项参与结算、查询条件或索引——一个从不被 `WHERE` 引用的列，拆细没有收益。而拆成四列意味着加第五项时要同时改 CHECK、迁移、备份白名单三处，每一处漏了都不会报错。

**为什么默认是 `'{}'` 而不是展开的完整对象。** `'{}'` 的语义是「用户没设置过，全用代码默认」。这带来一个关键性质：**将来改默认值时，没有主动设置过的人会跟着新默认走**；而明确关掉过月历的人，库里留着 `{"showCalendar":false}`，不会被改掉。对应的实现是 `serializeHomePrefs` **只写与默认值不同的字段**——全量序列化会让「新默认」永远影响不到老用户，这是最容易写反的一条。

**解析失败一律退回默认值，不抛错。** `parseHomePrefs` 做的是**字段级**兜底：一个字段类型不对（例如 `todoLimit: "nope"`）只让那一个字段回默认，不会把同一行里别的正确设置一起丢掉。整列不是合法 JSON 时才整列回默认。理由与 `getSafeDayStartHour` 相同：这一列只影响「长什么样」，不该有让首页白屏的权力。

**代价要说清**：用户手改坏了这一列，他**不会看到任何报错**，只会发现首页回到了默认的样子。可接受，因为他本来就没有任何入口能直接改这一列（只有设置页的开关）。

**备份必须同步（铁律二）**：`BACKUP_TABLES` 的 settings 白名单里必须有 `home_prefs`。漏了不会报错——用户的首页偏好会在「导出 → 导入」之后静默消失。`required` 里**不要**加它：v15 及更早的备份里没有这一列，加上会把用户手里所有旧备份判成坏文件。

**这一列不参与任何约束**：没有 CHECK、没有索引。取值合法性全在 `domain/homePrefs.ts` 的 `parseHomePrefs` 里，因为 JSON 内部的结构 SQLite 检查不了，写一个 `CHECK (json_valid(home_prefs))` 只能拦住「不是 JSON」，拦不住「todoLimit 是字符串」。

### 10.1 写什么

| 表 | 写入 | 数量 |
| --- | --- | --- |
| `player` | 名字「旅人」，1 级，XP 0，五维全 0，余烬 30（启程礼），材料 1 | 1 行 |
| `settings` | dayStart=4，难度=**easy**，主题=furnace，themeMode=system，`last_settled_date`=今天 | 1 行 |

| `checkins` | **0 行** | — |

### 10.2 为什么**不**预写示例任务

1. 示例任务会污染统计与连胜，用户还得先删。
2. 「今天」页应该展示用户自己的选择。
3. 模板应在引导页**内存中展示**，用户确认后才落库。

### 10.3 种子伪代码

```ts
export function seedIfEmpty(db: SQLiteDatabase): void {
  const exists = db.getFirstSync('SELECT id FROM player LIMIT 1');
  if (exists) return;   // 已有数据，不重复种子

  const now = Date.now();
  const playerId = randomUUID();
  const today = businessDate(now, 4);

  db.withTransactionSync(() => {
    db.runSync(
      // avatar_id 由列默认值补上（'fox'）；那三列废弃的头像列不写
      `INSERT INTO player (id, display_name, level, xp_total, xp_in_level, highest_level,
                           ember, material, onboarding_done, created_at, updated_at)
       VALUES (?, '旅人', 1, 0, 0, 1, 30, 1, 0, ?, ?)`,
      [playerId, now, now]
    );

    db.runSync(
      `INSERT INTO settings (id, player_id, day_start_hour, last_settled_date,
                             difficulty, theme_id, theme_mode, max_seen_utc, created_at, updated_at)
       VALUES ('singleton', ?, 4, ?, 'easy', 'furnace', 'system', ?, ?, ?)`,
      [playerId, today, now, now, now]
    );
  });
}
```

> `last_settled_date` 设为**当天**，是为了让首次启动不触发「补算历史断签」。

### 9.9 v16 → v17：`settings` 加一列 `journal_prefs`（日记偏好，D65）

```sql
ALTER TABLE settings ADD COLUMN journal_prefs TEXT NOT NULL DEFAULT '{}';
```

| 列 | 类型 | 含义 |
| --- | --- | --- |
| `journal_prefs` | `TEXT NOT NULL DEFAULT '{}'` | 一个 JSON 对象：字数上限 / 历史条数 / 是否显示字数计数。`'{}'` = 全用代码默认 |

**为什么它是独立的一条，而不是并进 v16。** 这一条是事故换来的，值得写清楚：

`journal_prefs` 第一版被并进了 v16，理由是「v16 从未出过包，不算已发布迁移」。**那个理由错了。** D31 的判据不是「有没有出包」，而是**有没有在任何数据库上执行过**——而开发库当时已经到 v16 了。结果是迁移器看到 `user_version = 16` 就直接返回，这一列永远不存在，之后每一次读 `settings` 都报 `no such column: journal_prefs`：日结算、宽限券、月度奖励、连胜、日记、首页偏好全部失效，整个 App 每一页都读不出数据。

**为什么 20 个测试套件全绿也没拦住。** 所有套件都建**全新库**，全新库跑完整的迁移链，两列都会加上。要拦住这一类，必须有一个「在旧版本库上继续升级」的测试。`migrate-old-test`（21 项）就是为此新增的：它真造一个「版本已到 16、但缺 `journal_prefs`」的库，再跑 `migrate`，断言列被补上、默认值是 `'{}'`、并且 `getSettings()` 读得出来。

**这一列的规则与 `home_prefs` 完全相同**：`'{}'` = 全用代码默认、只写与默认不同的字段、字段级兜底、解析失败退回默认值。区别只有一处——它存的三项里有两项**不是外观**（字数上限影响写进库的内容、历史条数影响读多少行），所以单独一列，不并进 `home_prefs`。

**备份**：同样进 settings 白名单，`required` 里不加。
