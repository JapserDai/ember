# 04 · 数据模型与数值

> 本册前半部分是 **v0.1 要真正实现的 5 张表**，可以直接照着建库。
> 后半部分是完整设计（v0.4+ 才用到），现在**只看不写**。
> 数值表与 `02` 的三档难度表必须逐项一致。

## 0. 三条不可破坏的规则

1. **业务日一律用 `local_date TEXT`（`YYYY-MM-DD`）**，由「本地时间 + dayStart」推导。UTC 毫秒只用于审计与排序。
2. **奖励在写入时固化到行内**。以后调数值，不改历史记录。
3. **随机不参与任何数值计算**。随机只决定文案和动画，所以撤销重记没有经济收益。

---

## 第一部分：v0.1 的 5 张表

## 1. 为什么是这 5 张

v0.1 只做：任务 + 打卡 + XP/等级 + 五维 + 目标 + 导出。

这六件事需要的事实只有五类：

| 表 | 存什么 | 为什么不能合并 |
| --- | --- | --- |
| `tasks` | 你要做的事 | 长期存在，会被修改、归档 |
| `checkins` | 你做过的每一次记录 | 只追加，是 XP 的唯一来源，永不修改 |
| `player` | 你的等级、属性、余烬 | 单行快照，可随时由 checkins 重建 |
| `settings` | 日界、难度、主题 | 单行配置 |
| `goals` | 一句话目标 | 建表放在 v0.1，界面到阶段 3 才接；现在建好省一条迁移 |

**关键设计**：`checkins` 是**事实表**，`player` 是**快照表**。快照永远可以从事实重建，所以即使 player 数据坏了也不会丢历史。

## 2. 建表 SQL

```sql
-- ============================================================
-- 打开数据库时必须执行的 PRAGMA
-- ============================================================
PRAGMA journal_mode = WAL;      -- 读写并发更好，崩溃恢复更稳
PRAGMA foreign_keys = ON;       -- SQLite 默认关闭，每个连接都要开
PRAGMA synchronous = NORMAL;    -- WAL 下兼顾安全与性能
PRAGMA busy_timeout = 5000;     -- 写锁最多等 5 秒


-- ============================================================
-- 表 1：player —— 玩家快照（永远只有 1 行）
-- 这一行可以从 checkins 完全重建，坏了也不丢历史
-- ============================================================
CREATE TABLE IF NOT EXISTS player (
  id            TEXT PRIMARY KEY NOT NULL,   -- UUID，同时用作随机种子的一部分
  display_name  TEXT NOT NULL DEFAULT '旅人',

  -- 等级与经验
  level         INTEGER NOT NULL DEFAULT 1
                  CHECK (level BETWEEN 1 AND 50),
  xp_total      INTEGER NOT NULL DEFAULT 0
                  CHECK (xp_total >= 0),      -- 历史累计 XP
  xp_in_level   INTEGER NOT NULL DEFAULT 0
                  CHECK (xp_in_level >= 0),   -- 当前等级内的进度
  highest_level INTEGER NOT NULL DEFAULT 1
                  CHECK (highest_level BETWEEN 1 AND 50), -- 历史最高，撤销时不清零

  -- 五维属性：直接放 5 列，避免为 v0.1 多建一张表
  -- 每列存「属性 XP」，满 200 自动转 1 点（见 4.3）
  attr_body_xp    INTEGER NOT NULL DEFAULT 0 CHECK (attr_body_xp   BETWEEN 0 AND 199), -- 体魄
  attr_mind_xp    INTEGER NOT NULL DEFAULT 0 CHECK (attr_mind_xp   BETWEEN 0 AND 199), -- 心智
  attr_order_xp   INTEGER NOT NULL DEFAULT 0 CHECK (attr_order_xp  BETWEEN 0 AND 199), -- 秩序
  attr_spirit_xp  INTEGER NOT NULL DEFAULT 0 CHECK (attr_spirit_xp BETWEEN 0 AND 199), -- 心力
  attr_bond_xp    INTEGER NOT NULL DEFAULT 0 CHECK (attr_bond_xp   BETWEEN 0 AND 199), -- 联结
  attr_body_pts   INTEGER NOT NULL DEFAULT 0 CHECK (attr_body_pts   >= 0),  -- 已获得的属性点
  attr_mind_pts   INTEGER NOT NULL DEFAULT 0 CHECK (attr_mind_pts   >= 0),
  attr_order_pts  INTEGER NOT NULL DEFAULT 0 CHECK (attr_order_pts  >= 0),
  attr_spirit_pts INTEGER NOT NULL DEFAULT 0 CHECK (attr_spirit_pts >= 0),
  attr_bond_pts   INTEGER NOT NULL DEFAULT 0 CHECK (attr_bond_pts   >= 0),

  -- 货币
  ember         INTEGER NOT NULL DEFAULT 0 CHECK (ember >= 0),      -- 余烬（软货币）
  material      INTEGER NOT NULL DEFAULT 0 CHECK (material >= 0),   -- 材料（硬货币，v0.4 才用）

  onboarding_done INTEGER NOT NULL DEFAULT 0 CHECK (onboarding_done IN (0,1)),

  -- 头像的重掷计数：图案由 (id, avatar_seed) 算出来，图片本身不存
  avatar_seed   INTEGER NOT NULL DEFAULT 0 CHECK (avatar_seed >= 0),

  created_at    INTEGER NOT NULL,
  updated_at    INTEGER NOT NULL
);


-- ============================================================
-- 表 2：settings —— 设置（永远只有 1 行，id 固定为 'singleton'）
-- ============================================================
CREATE TABLE IF NOT EXISTS settings (
  id               TEXT PRIMARY KEY NOT NULL DEFAULT 'singleton'
                     CHECK (id = 'singleton'),
  player_id        TEXT NOT NULL REFERENCES player(id) ON DELETE CASCADE,

  -- 业务日
  day_start_hour   INTEGER NOT NULL DEFAULT 4
                     CHECK (day_start_hour BETWEEN 0 AND 23),
  last_settled_date TEXT,        -- 上次结算的业务日；首次启动时设为当天
  week_starts_on   INTEGER NOT NULL DEFAULT 1 CHECK (week_starts_on IN (0,1)), -- 1=周一

  -- 难度与外观
  difficulty       TEXT NOT NULL DEFAULT 'easy'
                     CHECK (difficulty IN ('easy','standard','hard')),  -- 默认轻松
  theme_id         TEXT NOT NULL DEFAULT 'furnace'
                     CHECK (theme_id IN ('furnace','nightvoyage','tundra','daybreak')),
  theme_mode       TEXT NOT NULL DEFAULT 'system'
                     CHECK (theme_mode IN ('system','light','dark')),
  reduce_motion    INTEGER NOT NULL DEFAULT 0 CHECK (reduce_motion IN (0,1)),
  haptics_enabled  INTEGER NOT NULL DEFAULT 1 CHECK (haptics_enabled IN (0,1)),

  -- 时钟异常检测
  max_seen_utc     INTEGER NOT NULL DEFAULT 0,   -- 见过的最大时间戳，用于检测回拨
  last_time_zone   TEXT,                          -- 上次记录的时区，变更时重排通知

  created_at       INTEGER NOT NULL,
  updated_at       INTEGER NOT NULL
);


-- ============================================================
-- 表 3：tasks —— 三类任务（习惯 / 待办 / 奖励）
-- 单表 + type 判别键，理由见第 3 节
-- ============================================================
CREATE TABLE IF NOT EXISTS tasks (
  id               TEXT PRIMARY KEY NOT NULL,
  player_id        TEXT NOT NULL REFERENCES player(id) ON DELETE CASCADE,

  title            TEXT NOT NULL CHECK (length(trim(title)) BETWEEN 1 AND 80),
  notes            TEXT,

  -- 类型
  type             TEXT NOT NULL CHECK (type IN ('habit','todo','reward')),

  -- 重复规则
  recurrence       TEXT NOT NULL CHECK (recurrence IN (
                     'daily',        -- 每天
                     'weekly_days',  -- 每周固定几天
                     'monthly_days', -- 每月固定几号
                     'every_x_days', -- 每 N 天
                     'weekly_times', -- 每周 N 次（灵活）
                     'once'          -- 一次性（待办/奖励）
                   )),
  recurrence_config TEXT NOT NULL DEFAULT '{}',   -- JSON，见 3.3
  anchor_date      TEXT,      -- every_x_days 的锚点业务日
  interval_n       INTEGER CHECK (interval_n IS NULL OR interval_n BETWEEN 1 AND 365),
  weekly_target    INTEGER CHECK (weekly_target IS NULL OR weekly_target BETWEEN 1 AND 7),

  start_date       TEXT NOT NULL,   -- 生效业务日
  end_date         TEXT,            -- 结束业务日（含）
  due_date         TEXT,            -- 待办截止日

  status           TEXT NOT NULL DEFAULT 'active'
                     CHECK (status IN ('active','paused','done','archived')),
  completed_at     INTEGER,         -- 待办完成时间（毫秒）

  -- 五维属性归属
  attribute        TEXT NOT NULL
                     CHECK (attribute IN ('body','mind','order','spirit','bond')),

  -- 显示
  icon             TEXT,
  color            TEXT,
  sort_order       INTEGER NOT NULL DEFAULT 0,

  -- 打卡控制
  max_per_day      INTEGER NOT NULL DEFAULT 1 CHECK (max_per_day BETWEEN 1 AND 10),
  allow_backfill   INTEGER NOT NULL DEFAULT 1 CHECK (allow_backfill IN (0,1)),

  -- 奖励类专用
  ember_cost       INTEGER NOT NULL DEFAULT 0 CHECK (ember_cost >= 0),

  -- 关联目标（可选）。一个任务最多属于一个目标
  -- 不加外键约束：goals 表在本表之后创建，且目标删除是软删除，
  -- 由 repo 层在删除目标时把关联任务的 goal_id 置空，比外键更可控
  goal_id          TEXT,

  created_at       INTEGER NOT NULL,
  updated_at       INTEGER NOT NULL,
  deleted_at       INTEGER,        -- 软删除：NULL = 未删除

  -- 类型与重复规则必须自洽：习惯不能用 once，待办/奖励必须是 once
  CHECK (
    (type = 'habit' AND recurrence IN ('daily','weekly_days','monthly_days','every_x_days','weekly_times'))
    OR (type IN ('todo','reward') AND recurrence = 'once')
  ),
  -- weekly_times 必须给 weekly_target
  CHECK (recurrence <> 'weekly_times' OR weekly_target IS NOT NULL),
  -- every_x_days 必须给 interval_n 与 anchor_date
  CHECK (recurrence <> 'every_x_days' OR (interval_n IS NOT NULL AND anchor_date IS NOT NULL))
);

CREATE INDEX IF NOT EXISTS idx_tasks_player_status
  ON tasks (player_id, status, type) WHERE deleted_at IS NULL;
CREATE INDEX IF NOT EXISTS idx_tasks_due
  ON tasks (player_id, due_date) WHERE deleted_at IS NULL;


-- ============================================================
-- 表 4：checkins —— 打卡事实表（只追加，是 XP 的唯一来源）
-- 每一次记录一行，永不修改，撤销用 status='reversed' 标记
-- ============================================================
CREATE TABLE IF NOT EXISTS checkins (
  id             TEXT PRIMARY KEY NOT NULL,
  player_id      TEXT NOT NULL REFERENCES player(id) ON DELETE CASCADE,
  task_id        TEXT NOT NULL REFERENCES tasks(id) ON DELETE RESTRICT,

  -- 业务日
  local_date     TEXT NOT NULL
                   CHECK (local_date GLOB '[0-9][0-9][0-9][0-9]-[0-9][0-9]-[0-9][0-9]'),
  score_count    INTEGER NOT NULL DEFAULT 0 CHECK (score_count >= 0),  -- 同日第几次（0 基）
  occurred_at    INTEGER NOT NULL,     -- 真实发生时间（毫秒），只用于排序

  source         TEXT NOT NULL DEFAULT 'manual'
                   CHECK (source IN ('manual','backfill','import')),
  status         TEXT NOT NULL DEFAULT 'active'
                   CHECK (status IN ('active','reversed')),

  -- 奖励明细：写入时固化，以后调数值不改历史
  base_xp        INTEGER NOT NULL CHECK (base_xp >= 0),
  xp_awarded     INTEGER NOT NULL CHECK (xp_awarded >= 0),
  base_ember     INTEGER NOT NULL CHECK (base_ember >= 0),
  ember_awarded  INTEGER NOT NULL CHECK (ember_awarded >= 0),
  attr_key       TEXT NOT NULL
                   CHECK (attr_key IN ('body','mind','order','spirit','bond')),
  attr_xp_awarded INTEGER NOT NULL CHECK (attr_xp_awarded >= 0),
  multiplier     REAL NOT NULL CHECK (multiplier >= 0),  -- 难度 × 补记比例
  is_capped      INTEGER NOT NULL DEFAULT 0 CHECK (is_capped IN (0,1)),

  -- 随机（只影响文案与动画，不影响数值）
  prng_seed      TEXT NOT NULL,
  flavor_key     TEXT,

  reversed_at    INTEGER,
  reverse_reason TEXT,

  created_at     INTEGER NOT NULL,
  updated_at     INTEGER NOT NULL,

  -- 同一任务同一天的第 N 次唯一
  UNIQUE (task_id, local_date, score_count)
);

-- 同一任务同一业务日只能有一条有效记录（撤销后可重记）
CREATE UNIQUE INDEX IF NOT EXISTS uq_checkin_active
  ON checkins (task_id, local_date)
  WHERE status = 'active';

CREATE INDEX IF NOT EXISTS idx_checkins_player_date
  ON checkins (player_id, local_date, status);
CREATE INDEX IF NOT EXISTS idx_checkins_task_date
  ON checkins (task_id, local_date, status);


-- ============================================================
-- 表 5：goals —— 目标（界面在阶段 3 才接，表现在就建好）
-- 一句话目标 + 可选截止日。没有子目标、没有阶段、没有百分比。
-- 进度不存字段，每次由「关联任务完成了几个 / 一共几个」现算。
-- ============================================================
CREATE TABLE IF NOT EXISTS goals (
  id            TEXT PRIMARY KEY NOT NULL,
  player_id     TEXT NOT NULL REFERENCES player(id) ON DELETE CASCADE,

  title         TEXT NOT NULL CHECK (length(trim(title)) BETWEEN 1 AND 80),
  why           TEXT,                 -- 为什么想走这一段（可选）
  due_date      TEXT,                 -- 不填就是不限期，不显示倒计时

  status        TEXT NOT NULL DEFAULT 'active'
                  CHECK (status IN ('active','done','archived')),
  completed_at  INTEGER,

  sort_order    INTEGER NOT NULL DEFAULT 0,
  created_at    INTEGER NOT NULL,
  updated_at    INTEGER NOT NULL,
  deleted_at    INTEGER,

  CHECK (due_date IS NULL
         OR due_date GLOB '[0-9][0-9][0-9][0-9]-[0-9][0-9]-[0-9][0-9]')
);

CREATE INDEX IF NOT EXISTS idx_goals_player_status
  ON goals (player_id, status, sort_order) WHERE deleted_at IS NULL;

CREATE INDEX IF NOT EXISTS idx_tasks_goal
  ON tasks (goal_id) WHERE goal_id IS NOT NULL AND deleted_at IS NULL;


-- ============================================================
-- 版本记录（用 SQLite 内置的 user_version，不额外建表）
-- 首次建库后执行：PRAGMA user_version = 2;
-- v1 → v2 见 §9.3：settings 重建（theme_id 加 daybreak）+ player 加 avatar_seed
-- ============================================================
```

## 3. 为什么用单表存三类任务

| 理由 | 说明 |
| --- | --- |
| 共享字段占绝大多数 | 标题、备注、属性、排序、图标、颜色、状态、起止日期、软删除、时间戳，三类完全一致 |
| 「今天」页面要统一查询排序 | 习惯和待办要混排。单表一条 `WHERE` 就行；拆表要 3 次查询 + 内存归并 |
| 打卡外键只能指向一张表 | 拆表后 `checkins.task_id` 就得变成多态外键，SQLite 无法做真外键约束 |
| 加字段只改一处 | SQLite 的 `ALTER TABLE` 能力有限，拆表后每次加字段改 3 张表 |
| 判别键可以用 CHECK 强制约束 | 上面 DDL 里已经保证「习惯不能用 once」这类脏数据进不来 |

**只有约 8 个稀疏列**（`weekly_target / interval_n / ember_cost / due_date` 等），SQLite 存 NULL 的成本极低。

### 3.1 三种类型的行为差异

| | 习惯 habit | 待办 todo | 奖励 reward |
| --- | --- | --- | --- |
| 出现位置 | 每天（按重复规则） | 直到完成 | 奖励区 |
| 完成后 | 明天还会出现 | 消失，进回忆 | 消耗余烬 |
| 连胜 | 有 | 无 | 无 |
| 重复规则 | 5 种 | `once` | `once` |
| 奖励 | 产出 XP + 余烬 | 产出 XP + 余烬 | **只消耗** |

### 3.2 重复规则的存储

| 规则 | `recurrence` | 关键字段 / `recurrence_config` |
| --- | --- | --- |
| 每天 | `daily` | 无 |
| 每周一三五 | `weekly_days` | `{"days":[1,3,5]}`，1=周一 |
| 每月 1 号和 15 号 | `monthly_days` | `{"days":[1,15]}` |
| 每 3 天 | `every_x_days` | `interval_n=3, anchor_date='2026-10-01'` |
| 每周 3 次（灵活） | `weekly_times` | `weekly_target=3` |
| 一次性 | `once` | `due_date` 可选 |

**「每周 N 次」不建周进度表。** 进度由 checkins 按业务周聚合得出：

```sql
SELECT COUNT(*) FROM checkins
WHERE task_id = ? AND local_date BETWEEN ? AND ? AND status = 'active';
```

### 4.3 五维属性成长

- **200 属性 XP = 1 属性点**，余数保留。
- 属性点**纯展示**：解锁称号与图鉴，**不影响任何数值**。

| 任务类型 | 每次属性 XP（标准） | 多少次 = 1 点 |
| --- | ---: | ---: |
| 习惯·每日 | 20 | 10 次 |
| 习惯·每周 N 次 | 18 | 12 次（余 16） |
| 待办 | 50 | 4 次 |

属性点上限 99。**无衰减、不清零、不可跨维度使用。**

### 4.4 每日软上限（防刷）

```
XP 软上限   = 150 + 25 × 当前等级
余烬软上限 = 15 + 3 × 当前等级
绝对硬上限 = 3,000 XP / 日
```

| 等级 | XP 软上限 | 余烬软上限 |
| ---: | ---: | ---: |
| 1 | 175 | 18 |
| 5 | 275 | 30 |
| 10 | 400 | 45 |
| 20 | 650 | 75 |
| 30 | 900 | 105 |
| 40 | 1,150 | 135 |
| 50 | 1,400 | 165 |

- 额度内 100%；**XP 超出部分 25%**；属性 XP 超出部分 25%；**余烬超出部分 0%**。
- **分段计算**，不是一刀切：例如额度剩 10，本次原始 30 → `10 + floor(20 × 0.25) = 15`。
- 目标/连胜/升级等一次性奖励**不占软上限**。

| 补记窗口（从业务日结束算） | 72 小时 | 48 小时 | 24 小时 |
| 补记收益比例 | 100% | 70% | 40% |
| 每日软上限公式 | 相同 | 相同 | 相同 |

**补充规则**

- 断签扣减只在**修复期结束仍未修复**时执行。修复成功则不扣。
- 难度**不能**在 `repairable`（可修复）状态时修改，防止「断签后切轻松」套利。
- 宽限券在每月第一次结算时重置，不累积。
- 难度切换不追溯历史：已扣的不返还，已发的奖励不收回。

## 5. 核心事务：一次打卡

### 5.1 涉及的表与顺序

一次 `scoreTask` 必须在**同一个事务**内完成，否则会出现「打卡成功但没加 XP」。

```
BEGIN TRANSACTION
  1. 校验：任务存在、属于本人、未删除、未暂停
  2. 校验：targetDate 不是未来
  3. 校验：今天这次数 < max_per_day
  4. 校验：补记窗口内（若 source = backfill）
  5. 计算基础奖励（类型 + 难度）
  6. 应用补记折扣（若补记）
  7. 应用每日软上限（读今日已获得量）
  8. 写 checkins 一行（固化所有数值）
  9. 更新 player：xp_total、level、xp_in_level、属性、余烬
 10. 若是待办：更新 tasks.status = 'done'
COMMIT
```

### 5.2 伪代码（中文注释）

```ts
/**
 * 完成一次打卡。全部写操作在一个事务里。
 * 返回本次实际获得的奖励，供 UI 播放动画。
 */
export function scoreTask(input: {
  taskId: string;
  targetDate: string;      // 业务日
  source: 'manual' | 'backfill';
  nowMs: number;
}): ScoreResult {
  return db.withTransactionSync(() => {
    // ---------- 1. 读取 ----------
    const task = getTask(input.taskId);
    if (!task || task.deletedAt) throw new DomainError('TASK_NOT_FOUND');
    if (task.status === 'paused') throw new DomainError('TASK_PAUSED');

    const settings = getSettings();
    const player = getPlayer();
    const today = businessDate(input.nowMs, settings.dayStartHour);

    // ---------- 2. 拒绝未来日期 ----------
    if (diffDays(today, input.targetDate) > 0) {
      throw new DomainError('FUTURE_DATE');   // targetDate 在未来
    }

    // ---------- 3. 当日次数限制 ----------
    const todayCount = countActiveCheckins(task.id, input.targetDate);
    if (todayCount >= task.maxPerDay) throw new DomainError('ALREADY_DONE');

    // ---------- 4. 补记窗口 ----------
    const profile = DIFFICULTY[settings.difficulty];
    if (input.source === 'backfill') {
      const dayEnd = businessDayEndMs(input.targetDate, settings.dayStartHour);
      const hoursSince = (input.nowMs - dayEnd) / 3_600_000;
      if (hoursSince > profile.backfillWindowHours) {
        throw new DomainError('BACKFILL_EXPIRED');
      }
    }

    // ---------- 5–7. 计算奖励 ----------
    const base = BASE_REWARD[task.type];           // 见 4.2
    let multiplier = profile.rewardMult;           // 难度倍率
    if (input.source === 'backfill') {
      multiplier *= profile.backfillRatio;         // 补记折扣
    }

    // 软上限：先算原始值，再按剩余额度分段打折
    const todayXp = sumTodayXp(input.targetDate);
    const todayEmber = sumTodayEmber(input.targetDate);
    const capXp = 150 + 25 * player.level;
    const capEmber = 15 + 3 * player.level;

    const rawXp = Math.round(base.xp * multiplier);
    const rawEmber = Math.round(base.ember * multiplier);
    const xpAwarded = applySoftCap(rawXp, todayXp, capXp, 0.25);
    const emberAwarded = applySoftCap(rawEmber, todayEmber, capEmber, 0);
    const attrXp = Math.round(base.attrXp * multiplier);
    const isCapped = xpAwarded < rawXp ? 1 : 0;

    // ---------- 8. 写事实行 ----------
    const seedStr = `${player.id}|${input.targetDate}|${task.id}|${todayCount}`;
    const checkinId = randomUUID();
    insertCheckin({
      id: checkinId,
      playerId: player.id,
      taskId: task.id,
      localDate: input.targetDate,
      scoreCount: todayCount,
      occurredAt: input.nowMs,
      source: input.source,
      status: 'active',
      baseXp: base.xp,
      xpAwarded,
      baseEmber: base.ember,
      emberAwarded,
      attrKey: task.attribute,
      attrXpAwarded: attrXp,
      multiplier,
      isCapped,
      prngSeed: seedStr,
      flavorKey: pickFlavor(seedStr),   // 只决定文案，不影响数值
    });

    // ---------- 9. 更新快照 ----------
    const xpTotal = player.xpTotal + xpAwarded;
    const { level, inLevel } = levelFromTotalXp(xpTotal);

    const attr = growAttribute(player, task.attribute, attrXp);  // 满 200 转 1 点

    updatePlayer({
      xpTotal,
      xpInLevel: inLevel,
      level,
      highestLevel: Math.max(player.highestLevel, level),
      ...attr.patch,
      ember: player.ember + emberAwarded,
      updatedAt: input.nowMs,
    });

    // 升级奖励
    if (level > player.level) {
      for (let l = player.level + 1; l <= level; l++) {
        addEmber(10);   // 每级 10 余烬
      }
    }

    // ---------- 10. 待办标记完成 ----------
    if (task.type === 'todo') {
      updateTask(task.id, { status: 'done', completedAt: input.nowMs });
    }

    return { checkinId, xpAwarded, emberAwarded, attrXp, levelUp: level > player.level, level, isCapped };
  });
}
```

### 5.3 撤销

**允许条件**：该记录所在业务日**尚未结算**（`local_date >= last_settled_date`）。

```ts
/**
 * 撤销一次打卡。
 * 已结算的日子不允许撤销——只能靠导入导出修正。
 */
export function undoCheckin(checkinId: string, reason: string): void {
  return db.withTransactionSync(() => {
    const ck = getCheckin(checkinId);
    if (!ck || ck.status !== 'active') return;   // 幂等：已撤销

    const settings = getSettings();
    if (diffDays(settings.lastSettledDate ?? ck.localDate, ck.localDate) > 0) {
      throw new DomainError('DAY_ALREADY_SETTLED');
    }

    // 1. 标记事实行（不删除，保留审计）
    updateCheckin(ck.id, { status: 'reversed', reversedAt: Date.now(), reverseReason: reason });

    // 2. 扣回 XP 并重算等级（允许视觉降级，highest_level 保留）
    const player = getPlayer();
    const xpTotal = Math.max(0, player.xpTotal - ck.xpAwarded);
    const { level, inLevel } = levelFromTotalXp(xpTotal);
    updatePlayer({ xpTotal, xpInLevel: inLevel, level, ember: Math.max(0, player.ember - ck.emberAwarded) });

    // 3. 扣回属性
    regressAttribute(ck.attrKey, ck.attrXpAwarded);

    // 4. 待办重新打开
    const task = getTask(ck.taskId);
    if (task.type === 'todo') {
      updateTask(task.id, { status: 'active', completedAt: null });
    }
  });
}
```

### 5.4 防刷清单

| 手段 | 实现 |
| --- | --- |
| 重复打卡 | `uq_checkin_active` 唯一索引 + `max_per_day` |
| 双击/重试 | 唯一索引捕获 `SQLITE_CONSTRAINT` 后返回「已完成」 |
| 未来日期 | `scoreTask` 拒绝 `targetDate > today` |
| 无限补记 | 补记窗口（72/48/24 小时）+ 补记折扣 |
| 单日刷量 | 软上限 + 绝对硬上限 3000 XP |
| 改系统时间 | 业务日单调钳制（见 6.3） |
| 撤销重摇 | **随机不影响数值**，撤销重记得到相同数值 |

## 6. 惰性日结算

### 6.1 为什么不后台跑

App 不联网、不做常驻后台。**结算发生在「打开 App 时」**，这叫惰性结算（lazy evaluation）。

好处：即使一周没打开，数据也不会错——打开时补算即可。

### 6.2 结算规则

| 条件 | 行为 |
| --- | --- |
| `last_settled_date` 为空 | 首次启动：设为今天，**不结算任何历史** |
| 今天 < last_settled_date | 时钟回拨：不结算，标记异常，沿用旧值 |
| diff = 0 | 今天已处理：跳过 |
| diff = 1 | 结算昨天 |
| **diff > 1** | **只结算昨天一天**，并记录断签天数（继承 Habitica 的 `multiDaysCountAsOneDay`） |

> **为什么 diff > 1 只结算一天**：断签 10 天和断签 1 天，在习惯养成上的实际影响几乎一样（Lally 2010）。逐日结算只会产生大量无意义的惩罚记录，且用户会觉得被「追着罚」。

### 6.3 伪代码

```ts
export function settleUpTo(nowMs: number): SettleResult {
  return db.withTransactionSync(() => {
    const settings = getSettings();
    const player = getPlayer();
    const rawToday = businessDate(nowMs, settings.dayStartHour);

    // ---------- 时钟回拨保护 ----------
    if (nowMs < settings.maxSeenUtc - 3 * 3_600_000) {
      markClockAnomaly();   // 只标记，不惩罚
    }
    if (nowMs > settings.maxSeenUtc) {
      updateSettings({ maxSeenUtc: nowMs });
    }

    // ---------- 首次启动 ----------
    if (!settings.lastSettledDate) {
      updateSettings({ lastSettledDate: rawToday });
      return { skipped: true, reason: 'first_run' };
    }

    // ---------- 回拨：业务日不倒退 ----------
    if (diffDays(settings.lastSettledDate, rawToday) < 0) {
      return { skipped: true, reason: 'clock_back' };
    }

    // ---------- 同一天 ----------
    if (settings.lastSettledDate === rawToday) {
      return { skipped: true, reason: 'same_day' };
    }

    // ---------- 结算昨天（只结算一天）----------
    const diff = diffDays(settings.lastSettledDate, rawToday);
    const target = addDays(rawToday, -1);

    const hadRecord = countActiveCheckinsOn(target) > 0;

    // 连胜状态机（v0.2 启用；v0.1 只记录 streak 天数）
    const streakResult = advanceStreak({ target, hadRecord, difficulty: settings.difficulty });

    updateSettings({ lastSettledDate: rawToday });

    return {
      skipped: false,
      settledDate: target,
      gapDays: diff - 1,
      hadRecord,
      streak: streakResult,
    };
  });
}
```

### 6.4 触发时机

- App 冷启动，数据库初始化后
- 从后台回到前台
- 导入数据完成后
- 前台跨过 dayStart 时（设一个定时器到下一个切换点）

### 7.2 三态

```
                  有记录
        ┌──────────────────────┐
        │                      ▼

   │ normal  │──────────────▶│ normal  │（桥接，不增加天数）

   └─────────┘
```

### 7.3 规则细节

| 规则 | 说明 |
| --- | --- |
| 什么算「有记录」 | 该业务日至少一条 `status='active'` 的 checkin |
| 宽限券 | **一券桥接一天**。桥接日不计入 `current`，但让下一天可以继续 +1 |
| 修复 | 一次修复覆盖整个断签缺口；恢复值 = `frozen_current + 断签后连续成功天数` |
| 修复期限 | `break_date` 的业务日结束点 + **48 小时**。长期不打开，期限照常流逝 |
| 修复成本 | 轻松 15 余烬 / 标准 40 余烬+1 材料 / 硬核 100 余烬+3 材料 |
| 断签罚款 | 只在**修复期结束仍未修复**时扣。轻松 0，标准 5%（上限 30），硬核 10%（上限 80） |
| 永不降级 | 等级、物品、回忆、称号都不收回 |
| 连胜奖励去重 | `epoch + 阈值` 做唯一键；修复不换 epoch，不重复发奖 |

### 7.4 展示规则（重要）

断签后界面必须显示：

```

历史最佳：23 天
累计记录：147 天
```

**绝不显示「归零」「前功尽弃」。** 这三个数字并排，用户看到的是「我做过很多」，而不是「我失败了」。

## 8. 随机：种子化 PRNG

### 8.1 算法

```ts
/** FNV-1a 32 位哈希：把字符串压成种子 */
export function fnv1a32(input: string): number {
  let h = 0x811c9dc5;
  for (let i = 0; i < input.length; i++) {
    h ^= input.charCodeAt(i);
    h = Math.imul(h, 0x01000193);   // FNV 质数
  }
  return h >>> 0;
}

/** mulberry32：快速、确定、质量足够用于选文案 */
export function mulberry32(seed: number): () => number {
  let a = seed >>> 0;
  return function () {
    a = (a + 0x6d2b79f5) | 0;
    let t = Math.imul(a ^ (a >>> 15), 1 | a);
    t = (t + Math.imul(t ^ (t >>> 7), 61 | t)) ^ t;
    return ((t ^ (t >>> 14)) >>> 0) / 4294967296;
  };
}
```

### 8.2 种子拼接

```ts
// 规则：playerId | localDate | taskId | scoreCount
const seedStr = `${playerId}|${localDate}|${taskId}|${scoreCount}`;

// 每个用途再派生独立流，避免「多抽一次导致后续全变」
const flavorRand = mulberry32(fnv1a32(`${seedStr}|flavor`));
const animRand   = mulberry32(fnv1a32(`${seedStr}|anim`));
```

### 8.3 随机用在哪里

| 用途 | 影响数值？ |
| --- | --- |
| 打卡完成文案 | 否 |
| 探索事件选择 | 否（奖励固定区间，不随机大额） |
| 回忆卡封面图案 | 否 |
| **XP / 余烬 / 材料 / 属性** | **绝不使用随机** |

**这是防「撤销重摇」的根本手段**：随机只影响表现，重摇没有经济收益。

### 8.4 防改系统时间

| 攻击 | 防护 |
| --- | --- |
| 调回昨天重复打卡 | 业务日钳制 + 唯一索引 |
| 调快连续「过」很多天 | diff > 1 只结算一天，无法补领连胜 |
| 调到未来打卡 | `scoreTask` 拒绝未来日期 |
| 改时区绕过 dayStart | 业务日始终用本地时间；`max_seen_utc` 记录异常 |
| 回拨后重领升级奖励 | 升级奖励按等级去重，`highest_level` 保留 |

时钟异常只**标记**，不惩罚、不回滚——避免误伤跨时区旅行的用户。

## 9. 数据迁移

### 9.1 版本管理

用 SQLite 内置的 `PRAGMA user_version`，不额外建表。

```ts
const CURRENT_VERSION = 2;

const MIGRATIONS: Array<(db: SQLiteDatabase) => void> = [
  // 索引 0：从 0 升到 1 —— 建所有表
  (db) => { db.execSync(SCHEMA_SQL_V1); },
  // 索引 1：从 1 升到 2 —— 见 §9.3
  (db) => { db.execSync(MIGRATE_V1_TO_V2_SQL); },
];

export function migrate(db: SQLiteDatabase): void {
  const { user_version: current } = db.getFirstSync<{ user_version: number }>(
    'PRAGMA user_version'
  )!;

  // 降级保护：数据库比代码新
  if (current > CURRENT_VERSION) {
    throw new Error('这个数据库来自更新版本的 Ember，请升级 App 后再打开');
  }

  for (let v = current; v < CURRENT_VERSION; v++) {
    MIGRATIONS[v](db);
  }
  db.execSync(`PRAGMA user_version = ${CURRENT_VERSION}`);
}
```

### 9.2 迁移规则

1. **尽量只做加法**：新增列给默认值。改类型、改约束只能重建表（见 §9.3），代价高且要单独验证。
2. **已发布的迁移函数永远不修改**。
3. **每次迁移前复制一份数据库文件**，保留最近 2 份。
4. 导入旧版本 JSON 时，用同样的数组式迁移链处理数据文档，再写库。

### 9.3 唯一的例外：v1 → v2 重建了 settings

v2 做了两件事：

1. `settings.theme_id` 的 CHECK 加上 `'daybreak'`（第四套主题「晨光」）。
2. `player` 加一列 `avatar_seed INTEGER NOT NULL DEFAULT 0 CHECK (avatar_seed >= 0)`。

第 2 件是普通的加法。第 1 件不行：**SQLite 改不了 CHECK 约束**，只能「建新表 → 拷数据 → 删旧表 → 改名」。

为什么宁可重建，也不把 CHECK 去掉：
- `settings` 永远只有 1 行，重建成本可以忽略（一次 INSERT + 一次 DROP）。
- 没有 CHECK 时，`theme_id` 写进非法值，界面会静默回退到炉边，用户会以为「主题设置丢了」。宁可让非法值在写入时直接报错。

迁移 SQL 在 `src/db/schema.ts` 的 `MIGRATE_V1_TO_V2_SQL`，整段跑在迁移器的那一个事务里。要点：

| 要点 | 做法 | 为什么 |
| --- | --- | --- |
| 不用 `SELECT *` | 逐列写死列名 | 列顺序变了也不会错位 |
| 外键 | 新表的 `player_id` 声明与旧表一致 | `PRAGMA foreign_keys = ON` 下，表改名/重建期间外键仍然有效 |
| 索引 | `settings` 本来就没有显式索引，只有主键自带的 autoindex | 重建后自动跟着新表建好，不需要手工补 |
| 幂等 | 不幂等：靠 `user_version` 保证只跑一次 | 迁移链由版本号驱动，不需要每条迁移自己判重 |

### 10.3 种子伪代码

```ts
export function seedIfEmpty(db: SQLiteDatabase): void {
  const exists = db.getFirstSync('SELECT id FROM player LIMIT 1');
  if (exists) return;   // 已有数据，不重复种子

  const now = Date.now();
  const playerId = randomUUID();
  const today = businessDate(now, 4);

  db.withTransactionSync(() => {
    db.runSync(
      // avatar_seed 不写：列默认 0，含义是「还没换过」
      `INSERT INTO player (id, display_name, level, xp_total, xp_in_level, highest_level,
                           ember, material, onboarding_done, created_at, updated_at)
       VALUES (?, '旅人', 1, 0, 0, 1, 30, 1, 0, ?, ?)`,
      [playerId, now, now]
    );

    db.runSync(
      `INSERT INTO settings (id, player_id, day_start_hour, last_settled_date,
                             difficulty, theme_id, theme_mode, max_seen_utc, created_at, updated_at)
       VALUES ('singleton', ?, 4, ?, 'easy', 'furnace', 'system', ?, ?, ?)`,
      [playerId, today, now, now, now]
    );
  });
}
```

> `last_settled_date` 设为**当天**，是为了让首次启动不触发「补算历史断签」。

## A.3 为什么 v0.4 之后才需要「事实表 + 快照 + 审计」

| 机制 | 什么时候才值得 |
| --- | --- |
| `currency_ledger`（货币流水） | 有余烬消费（v0.4 商店）时，才需要能解释「这 40 余烬花在哪」 |
| `reward_grants`（奖励去重表） | 有目标奖励时，才需要防止重复发放 |
| `event_log`（事件审计） | 需要「为什么加了这个数」的解释（v0.9 回忆系统）时 |
| `daily_settlements`（结算审计） | 断签纠纷需要追溯（v0.2 连胜）时 |
| 不变量校验与重建函数 | 数据量超过几千行、或有导入导出损坏风险（v1.0）时 |

**在 v0.1 实现这些，收益为零，成本是几百行难调试的代码。**

## A.4 完整设计里值得保留的三个思路

即使暂不实现，这三条在设计 v0.1 时就已隐含：

1. **事实与快照分离**：v0.1 的 `checkins`（事实）与 `player`（快照）已经是这个结构。所以将来加 `currency_ledger` 不需要重构。
2. **奖励写入时固化**：`checkins` 里存 `xp_awarded` 而不是只存 `base_xp`，将来调数值不改历史。
3. **唯一键做幂等**：`uq_checkin_active` 就是最小版的幂等保障。
