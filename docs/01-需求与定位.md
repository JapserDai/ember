# 01 · 需求与定位

## 一句话

Ember 是一个只属于你的、会陪你慢慢来的离线人生小火堆。

## 要解决什么问题

大多数人不是不知道该怎么生活，而是**知道却坚持不下来**。

具体表现有三种：

1. **启动困难**：想读书、想运动，但每天就是开不了头。
2. **断签即放弃**：坚持了 20 天，第 21 天没做到，觉得「前功尽弃」，然后彻底不做了。
3. **目标悬空**：知道「今年想健康一点」，但不知道今天具体该做什么，或者每天做的事和长期目标没关联。

Habitica 用 RPG 外壳解决第 1 个，但用掉血惩罚**加重**了第 2 个。Finch 用陪伴解决第 2 个，但过度可爱筛掉了一批成年用户。Loop 用不清零的计分解决第 2 个，但完全没有情感联结。

Ember 想同时接住这三个问题，且**不做任何需要联网的事**。

## 用户是谁：理想与现实

这一节很重要，因为它决定后续所有取舍。

### 理想用户

想改善生活、试过 Habitica 或 Finch 但没坚持下来、愿意花几分钟每天记录一次的人。

### 现实用户

**「愿意从网页下载 apk、允许未知来源安装、绕过系统安全提示的人」。**

这两者之间有巨大落差。普通用户获取 App 的路径是「应用商店搜索 → 点安装」，而 Ember 的路径是：

> 打开网页 → 下载 apk → 系统提示「不允许安装未知来源应用」→ 去设置里找开关 → 返回 → 确认安装 → 系统提示「此应用未经安全检测」→ 选择「仍然安装」

**每一环都会流失大量用户。** 能走完这条路径的人，基本是技术爱好者、开发者、或你的朋友。

### 所以产品决策要这样定

| 决策 | 因为现实用户是这样的人，所以 |
| --- | --- |
| 不做新手引导的过度简化 | 他们能理解「日界」「连胜」这类概念，不需要哄小孩式的引导 |
| 不做社交、不做账号 | 他们更在意隐私和独立，而不是和陌生人比 |
| 文案可以克制、可以有难度 | 他们讨厌被当成需要鼓励的小孩（这正是 Finch 被批评的点） |
| 但安装说明必须极其清楚 | 因为这一步流失最严重，落地页要把每一步写明白 |
| 不追求用户量 | 免费、无服务器、无变现，用户量不是目标 |

**换句话说：「泛用户」是遥远目标，「愿意侧载的人」是当下真实用户。** 所有近期决策按后者做。

## 三类定位的主次

用户说「习惯养成 + 人生规划 + 自我关怀」都要。但三者不能平铺，必须有主次。

### 骨架：习惯养成

**它决定数据模型、每日循环、以及产品是否成立。**

理由：所有系统消费同一份原始事实——**打卡事件**。

```
打卡事件
  ├─ XP / 等级 / 余烬
  ├─ 五维属性成长
  ├─ 目标进度
  ├─ 周报 / 统计 / 日记
  └─ 连胜 / 宽限 / 修复
```

没有打卡，目标进度是空的，余烬没有来源，周报没有数字。习惯层是树干，其余是枝叶。

对零基础开发者还有两个现实理由：

- **反馈周期最短**：7 天就能验证「我会不会每天打开」。规划要几个月才看得出有没有用。
- **数据模型最稳定**：`tasks / checkins / player / settings / goals` 五张表定对，后面都是加表。

### 目标层：人生规划

**它消费打卡数据，不产生每日行动。**

规划以**简单目标**的形式存在：一句话目标，可选截止日，可选关联任务。进度按关联任务的完成数自动算，不显示百分比。关联是可选的，一个目标可以不挂任何任务；目标可以手动标记完成，也可以在关联任务全部完成时由系统提示。

围绕目标，规划只保留两种轻量形式，不变成每天必填的复杂计划表：

- **周复盘**：周日 3 个问题，5 分钟内可完成，跳过不惩罚。
- **月/季回看**：只在月末最后一个周末出现，不打断日常。

### 体验基调：自我关怀

**它是横切政策，不是一个页面。**

它决定：惩罚曲线、文案口吻、空状态设计、断签处理、视觉温度。它从 v0.1 就存在于每个交互里。

如果把它当模块排到最后，前面所有代码会写满羞辱性文案和惩罚逻辑，后期返工量远超新写。

### 排错了会怎样

| 错误排法 | 后果 |
| --- | --- |
| 规划当骨架 | 做成「高级待办清单 + 日记」，每天没有即时反馈，第 7 天弃用 |
| 关怀当模块 | 先写完硬核惩罚与失败文案，后期发现最大差评源就是它，需重写全部反馈层 |
| 收集当骨架 | 先做 90 只宠物和 200 件装备，任务系统只有 1 个原型，3 天玩完全部内容 |
| 叙事当骨架 | 先写 12 段剧情，结果没有可玩的循环承载剧情，读完后产品归零 |

**判断口诀**：能不能砍？砍掉后产品还成立吗？——砍掉收集/叙事/Boss，习惯+规划仍成立；砍掉习惯，一切归零。

## 差异化：中文原生、温柔但不幼稚

如果去掉品牌名，Ember 和竞品的区别是：

| 对比 | Habitica | Finch | Loop | **Ember** |
| --- | --- | --- | --- | --- |
| 语言 | 翻译腔，中文生硬 | 英文为主 | 英文 | **中文原生，像人写的** |
| 语气 | 奇幻 RPG，鼓励但冷 | 过度可爱，被批「想掐死那只鸟」 | 无语气 | **温柔、克制、不哄小孩** |
| 惩罚 | 掉血、死亡、掉级 | 无 | 无 | **无，且可修复** |
| 联网 | 必须联网 | 需要账号 | 不需要 | **完全离线，无网络权限** |
| 社交 | 队伍、公会、排行榜 | Tree Town | 无 | **完全没有** |
| 复杂度 | 极高，像第二份工作 | 中 | 极简 | **中，但有深度** |
| 平台 | 双端 | 双端 | 仅 Android | **仅 Android** |

### 「温柔但不幼稚」的具体落地

这不是一句口号，要能落到每一句文案上。

**温柔**意味着：
- 断签后第一句话是「你回来了」，不是「你失败了」。
- 提到中断时归因外部：「这周很忙吧」，而不是「你没坚持住」。
- 从不假装有情感：「火还亮着」比「我一直在等你」更可信。

**不幼稚**意味着：
- 不用叠词、不用颜文字、不连用感叹号。
- 不把用户当需要哄的小孩，承认做一件事有时候就是很难。
- 可以有难度、可以有沉默，不是每句话都要「加油」。

**语气由文案承担，不由配色承担。** 原规划里四套主题各对应一种语气（详见 `02` §1）；v0.1 只保留了一套白底主题（D27），所以下面这张表暂时只是参考，等主题回来时才会真正生效：

| 主题 | 气质 | 同一句话的说法 |
| --- | --- | --- |
| 炉边 | 傍晚回到家，有人替你把炉火拨亮 | 「昨天炉子凉了一点，不碍事。现在添一根柴，火就回来了。」 |
| 夜航 | 深夜驾驶舱，仪表微亮 | 「昨天没有记录。数据还在，连胜进入可修复状态，剩余 47 小时。」 |
| 苔原 | 白天的窗边书桌，纸和铅笔 | 「昨天空了一天。习惯不会因为一天就消失，今天想从哪一件小事重新开始？」 |

同一件事、三种说法、没有一句在指责。这就是「温柔但不幼稚」。

## 明确不做的事

以下功能**永远不做**，不是推迟。

| 不做的 | 理由 |
| --- | --- |
| 账号系统 / 云同步 | 硬约束：无账号、无服务器 |
| 社交（好友、队伍、公会、排行榜、私信） | 与「不比较、只关怀」的基调直接冲突；无审核能力 |
| 多人 Boss / 世界事件 | 需要全局状态同步 |
| 宝石 / 订阅 / 内购 / 广告 | 硬约束：免费、无商业化 |
| 死亡 / 掉级 / 没收资产 | 调研明确：Habitica 最大差评源 |
| 带数值的装备与战斗 | 数值平衡对单人开发者是黑洞，且与「不惩罚」冲突 |
| 职业系统（战士/法师/盗贼/治疗） | 引入技能、法力、战斗数值，复杂度爆炸；五维已能表达差异 |
| 负向习惯（扣分按钮） | 等于让用户每天主动扣自己分 |
| iOS 版本 | 用户没有 iPhone；成本与风险不成比例 |
| Google Play / 国内应用商店 | 审核成本、测试门槛、备案要求都不值得 |
| 多语言 | 硬约束：仅中文 |
| 联网 AI / 聊天伴侣 | 无服务器；普通用户不会填 API Key |
| 任务分享到社交 | 无社交；只支持导出给自己存档 |

## 竞品的关键教训

调研了 Habitica、Finch、Forest、Streaks、Habitify、Loop、Fabulous、EpicWin、LifeUp 后的核心结论：

| 教训 | 来源 | 我们的做法 |
| --- | --- | --- |
| **惩罚发生在用户最脆弱的时候** | Habitica 掉血死亡 | 永不惩罚，只断连胜且可修 |
| **断签的呈现方式本身就会降低后续投入** | Silverman & Barasch (2023) | 断签后展示「历史最佳 + 累计天数」，不展示「归零」 |
| **漏一天对习惯形成几乎无影响** | Lally et al. (2010) | 归零在事实上是错误的反馈 |
| **不清零的计分更抗挫折** | Loop 的指数平滑强度分 | 用连胜做表层展示，暗线用累计天数 |
| **情感联结比可爱更持久** | Finch D1 54% / D7 37% | 不做会卖萌的角色；用等级、五维、连胜、称号这些长期数据与日记页承载「被记得」的感觉 |
| **过度可爱会筛掉成年用户** | Slate 批 Finch「想掐死那只鸟」 | 语气克制，不用叠词与颜文字 |
| **买断转订阅会引发老用户反弹** | Forest 评分暴跌 | 免费，不做任何商业化 |
| **只有皮肤没有系统，活不过两年** | EpicWin 停更 | 系统做骨架 |
| **只有系统没有内容，留不住普通用户** | LifeUp 学习成本高 | 系统 + 模板化内容 |
| **游戏行为不能产生 XP** | Habitica 的目标替代问题 | 只有现实任务产生 XP |

## 人升（LifeUp）逐项对照

人升是国内最接近本产品形态的参照：Android 单端、游戏化待办、属性等级、金币商店、成就系统。它的功能面比 Ember 宽得多，**但宽不等于对**——它的学习成本也是同类里最高的。

下面逐项过一遍。每一项都要回答「为什么采 / 为什么不采」，而不是「它有没有」。

### 采纳

| 人升的功能 | Ember 怎么改 | 为什么采 |
| --- | --- | --- |
| **成就系统**（成就清单 + 成就项，自动解锁） | 采纳，但**条件内置、用户不可自定义**。条件只从 Ember 自己的数据推导：累计打卡天数、某习惯连续 N 天、完成 N 个目标、五维达到阈值、首次导出备份 | 成就与「不惩罚、只记录」的基调完全契合：它只奖励「你做到了」，从不惩罚「你没做到」。但让人升式的「自定义条件」会让第一次用的人面对一张空表单 |
| **商店**（自定义商品，用金币兑换现实奖励） | 采纳。把现有「奖励」任务类型显性化成一页：列出你自己定的奖励（看一集剧、买一本书），标价余烬，点「兑换」即完成 | 余烬目前只有「修复连胜」一个出口，长期会永远花不完。人升证明「给自己定价」是这个系统里最有说服力的一环 |
| **统计卡片**（番茄占比、日均、属性变化、年度总结） | 采纳维度，换成 Ember 的：近 30 天完成率、最稳的习惯、最常记录的时段、五维变化、年度小结 | 统计是「日记」页的骨架。人升的维度选得准——它统计的是行为，不是分数 |

### 不采纳

| 人升的功能 | 不采的理由 |
| --- | --- |
| **自定义属性 / 技能** | 五维固定，才能让「称号由最高维推导」成立、让统计口径跨用户可比。让用户自己定义度量，等于让第一次用的人面对一道设计题 |
| **自定义等级梯度** | 等级曲线是唯一的进度尺，改了就失去参照。**但采纳其中一小部分**：每 5 级给一个称号（见 02 §3.4） |
| **仓库 / 库存** | 买了就用。多一层「已购未用」的状态，换不来任何体验 |
| **宝箱 / 开箱 / 盲盒** | 随机奖励与「每个数字都能解释」直接冲突，而且开箱本质是赌博机制。DECISIONS D7 已定随机不参与任何数值 |
| **合成**（N 个碎片换一件） | 收集经济的复杂度对单人开发者是黑洞，且需要一整套物品定义表 |
| **负向任务 / 失败扣钱** | D6 永不惩罚。这是人升与 Ember 最根本的分歧，没有折中空间 |
| **二维码打卡 / 购买** | 需要相机权限，与「不申请任何权限」的硬约束冲突 |
| **WebDAV 备份同步** | 需要网络权限。Ember 只做本地文件导出 / 导入 |
| **社区动态 / 关注** | 无账号、无服务器、无社交 |
| **番茄钟 / 专注计时** | 需要前台服务 + 通知 + 后台计时，是阶段 5 之后才值得碰的硬骨头。先进停车场（05 §12） |

### 从人升身上学到的一条

**人升的功能不缺，缺的是「第一次打开时该做什么」。** 它的属性、商店、成就、宝箱全部可自定义，等于把设计权交给了一个还不知道自己要什么的人。

Ember 的取舍是反过来的：**结构和条件全部内置，只把「内容」留给用户**——你写什么习惯、什么目标、什么奖励，是你的事；怎么算、怎么奖励、怎么展示，是产品的事。

## 成功标准

没有商业目标，成功标准只有三条，按顺序：

| 优先级 | 标准 | 怎么判断 |
| --- | --- | --- |
| 1 | **我自己连续用 30 天** | 看 App 里的记录，不看感觉 |
| 2 | **我自己连续用 90 天** | 同上。90 天是习惯成型的分水岭 |
| 3 | **3 位朋友装上并用了 7 天以上** | 不需要他们坚持，只需要他们真的用了 |

**明确不作为成功标准**：下载量、用户数、评分、收入。

如果第 1 条做不到，产品就是失败的，无论代码写得多好。
