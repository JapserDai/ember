# 03 · 技术方案

> 本册回答：用什么技术、怎么在 Windows 上出 apk、怎么发布、哪些坑要提前知道。

## 0. 一句话

**Expo SDK 58 + TypeScript + expo-sqlite + Reanimated + EAS 云构建。**

本机只需要 Node 和 Git。不需要 Java、Android Studio、Android SDK、Mac。

## 1. 技术栈

### 1.1 核心依赖

| 用途 | 选择 | 版本策略 |
| --- | --- | --- |
| 框架 | `expo` | SDK 58，锁死 |
| 语言 | TypeScript | 初期关闭 `strict`，熟练后再开 |
| 路由 | `expo-router` | 文件即路由，随 SDK |
| 数据库 | `expo-sqlite` | 原生 SQL，**不装 ORM** |
| 动画 | `react-native-reanimated` + `react-native-worklets` | 版本必须严格配对 |
| 图形 | `react-native-svg` | 头像、进度条、称号徽章；不装 Skia（D4） |
| 通知 | `expo-notifications` | 设计成增强，非核心 |
| 文件 | `expo-file-system`（新 API）+ `expo-document-picker` + `expo-sharing` | 导出导入 |
| 状态 | `zustand` | 只存 UI 瞬时状态 |
| 触感 | `expo-haptics` | 打卡反馈 |
| 字体 | `expo-font` | 四套主题的中文字体 |

### 1.2 明确不装的依赖

每一项都是升级时的雷，且本项目不需要。

| 不装 | 理由 |
| --- | --- |
| **Drizzle ORM / drizzle-kit** | 只有 4–8 张表。它需要 babel `inline-import` + metro `sourceExts` + `drizzle-kit generate` + `useMigrations` 四件事同时正确，任一错都表现为手机运行时报 `no such table`。零基础通过率约 30%，而手写 SQL 的通过率约 70% |
| **@shopify/react-native-skia** | universal apk 会增大约 41MB；1.x→2.x 有破坏性变更。本项目动效是装饰性的，Reanimated + SVG 足够 |
| **expo-updates** | 离线 App 不需要 OTA 更新，还会多一条网络依赖 |
| **任何同步框架**（PowerSync / ElectricSQL / WatermelonDB / Realm） | 无服务器、单设备，同步能力收益为零，只带来配置负担 |
| **任何 HTTP 客户端**（axios / fetch 封装） | App 不联网，不申请网络权限 |
| **Redux / TanStack Query** | 过度设计。Zustand + SQLite 查询足够 |
| **Jest / Detox 全套** | 只写纯函数单元测试（日期、数值），不需要 E2E |

## 3. 关键决策与理由

| 决策 | 选择 | 理由 |
| --- | --- | --- |
| 数据库访问 | 手写 SQL + 薄封装 | 4–8 张表不值得引入 ORM；手写 SQL 出错时错误信息直接指向语句 |
| 迁移方式 | `PRAGMA user_version` + 数组式迁移器 | 30 行代码，比任何 ORM 的迁移系统都好懂 |
| 日期处理 | 自写 `date.ts`，不装 dayjs/date-fns | 只需要业务日加减、星期、月份天数，30 行够用；少一个依赖 |
| 状态管理 | Zustand 只存 UI 状态 | 业务数据一律从 SQLite 查，不维护第二份真相 |
| 组件库 | 不用 UI 框架，自写基础组件 | 四套主题需要完全控制 token；UI 框架的主题系统反而碍事 |
| 图标 | `react-native-svg` 自绘或内联 SVG | 避免图标库的包体积与风格不一致 |

## 4. 日期与 dayStart（最容易出错的地方）

### 4.1 规则

1. **业务日 = `localDate: "YYYY-MM-DD"`**，由「设备本地时间 + `dayStart`」推导。
2. **绝不用 UTC 时间戳判断业务日。** UTC 只用于审计、排序、修复倒计时。
3. **`dayStart` 默认 4 点。** 凌晨 3:59 打卡算前一天，4:00 算新的一天。
4. **业务日只能前进。** 系统时间被调回过去时，沿用 `lastSettledDate`，不倒退。

### 4.2 唯一入口

全项目**只允许**通过 `src/domain/date.ts` 判断「今天」。任何地方出现 `new Date().getDate()` 之类的散装写法都是 bug。

```ts
// 业务日计算：本地时间 dayStartHour 点之前，仍属于前一个业务日
export function businessDate(nowMs: number, dayStartHour: number): string {
  const d = new Date(nowMs);
  // 用本地构造器得到「今天 dayStartHour 点」这个时间点，夏令时也正确
  const todayStart = new Date(
    d.getFullYear(), d.getMonth(), d.getDate(), dayStartHour, 0, 0, 0
  ).getTime();

  if (d.getTime() >= todayStart) return toDateKey(d);   // 已过切换点，算今天
  return toDateKey(new Date(d.getFullYear(), d.getMonth(), d.getDate() - 1, 12)); // 否则算昨天
}

// 两个业务日相差天数：用 UTC 日期序数计算，避免夏令时影响
export function diffDays(a: string, b: string): number {
  const [ay, am, ad] = a.split('-').map(Number);
  const [by, bm, bd] = b.split('-').map(Number);
  return Math.round((Date.UTC(by, bm - 1, bd) - Date.UTC(ay, am - 1, ad)) / 86_400_000);
}
```

### 4.3 必须写单元测试的边界

| 用例 | 期望 |
| --- | --- |
| `dayStart = 4`，时间 03:59 | 属于前一天 |
| `dayStart = 4`，时间 04:00 | 属于当天 |
| 跨月：10 月 31 日 03:00 | 属于 10 月 30 日 |
| 跨年：1 月 1 日 03:00 | 属于 12 月 31 日 |
| 用户把 `dayStart` 从 4 改成 0 | 历史记录不变，只影响「今天」的边界 |
| 系统时间回拨一天 | 业务日不倒退 |

**中国无夏令时**，风险比欧美低一半，但代码仍要写对——用户可能出国旅行。

## 5. 通知策略

### 5.1 定位：增强，不是核心

**App 打开时必须能补签，不依赖通知也能完整使用。** 这是硬性设计约束，因为国产 ROM 的后台管控会让通知不可靠。

### 5.2 iOS 的限制（虽然不做 iOS，但概念要懂）

- 每个 App 最多 64 条 pending 通知，超出**静默丢弃**，不报错。
- 一个 `repeats: true` 的日历触发器只占 1 个名额。

### 5.3 Android 的现实

| 问题 | 表现 | 应对 |
| --- | --- | --- |
| 精确闹钟权限 | Android 12+ 需 `SCHEDULE_EXACT_ALARM`，14 起新装不默认授予 | **不追求精确到分**。用 `setAndAllowWhileIdle`，可能延后几分钟到一小时 |
| 国产 ROM 后台管控 | 小米/华为/OPPO 杀后台后通知不响 | 引导页提示「允许自启动 / 关闭省电限制」；同时**不依赖通知** |
| force-stop | 用户「强行停止」会清空所有 alarm | 每次启动时补排 |
| 通知渠道 | Android 8+ 必须建 channel；13+ 需运行时权限 | 先建 channel 再请求权限 |

### 5.4 实现方案

```
每个提醒 → 1 个 daily 触发器（固定文案）
需要每日轮换文案 → 预排 7 天（7 个 identifier，带日期，便于取消）
启动 / 回前台 / 时区变化 → reconcileNotifications()：
    取消过期 → 补齐到 7 天 → 总数 ≤ 20
```

**总数控制在 20 条以内**，远低于任何平台上限。

### 5.5 时区变更检测

```ts
// 启动与回前台时比较当前时区与上次记录值，不同则重排所有通知
const currentZone = Intl.DateTimeFormat().resolvedOptions().timeZone;
if (currentZone !== settings.lastTimeZone) {
  await cancelAllScheduledNotificationsAsync();
  await reconcileNotifications();
  settings.lastTimeZone = currentZone;
}
```

这是 20 行工具函数，但漏了就会收到「我在国外没收到提醒」的问题。

## 6. 数据导出与导入

### 6.1 为什么第一版就要有

**离线 App 的用户数据只在手机上。** 换机、卸载、手机损坏，数据就没了。导出是唯一的保险，也是「体面退出」的前提。

### 6.2 实现

```ts
// 导出：写入文件 → 调起系统分享面板
const file = new File(Paths.cache, `ember-backup-${dateKey}.json`);
file.write(JSON.stringify(envelope, null, 2));
await Sharing.shareAsync(file.uri, {
  mimeType: 'application/json',
  dialogTitle: '保存 Ember 备份',
});

// 导入：选文件 → 校验 → 先备份当前库 → 事务内全量替换
const result = await DocumentPicker.getDocumentAsync({ copyToCacheDirectory: true });
```

### 6.3 信封结构

```jsonc
{
  "format": "ember.backup",
  "formatVersion": 1,
  "schemaVersion": 1,
  "appVersion": "0.1.0",
  "exportedAt": "2026-10-24T12:00:00.000Z",
  "device": { "platform": "android", "locale": "zh-CN", "timezone": "Asia/Shanghai", "dayStartHour": 4 },
  "counts": { "tasks": 12, "checkins": 340 },
  "checksum": "sha256:9f2c...",
  "data": {
    "player": { "...": "单对象" },
    "settings": { "...": "单对象" },
    "attributes": [],
    "tasks": [],
    "checkins": []
  }
}
```

**导入规则**

| 步骤 | 规则 |
| --- | --- |
| 1 | 文件 ≤ 50MB，JSON 可解析 |
| 2 | `format === 'ember.backup'` |
| 3 | `schemaVersion` ≤ 当前版本；高于则拒绝并提示升级 App |
| 4 | 重算 checksum 一致 |
| 5 | `counts` 与实际数组长度一致 |
| 6 | 外键完整（checkin 的 task_id 都存在） |
| 7 | **导入前自动把当前库复制一份**（`ember.pre-import.db`） |
| 8 | 事务内全量替换；失败则回滚 |
| 9 | 导入后重新计算快照（等级、属性），不信任文件里的派生值 |

**v1 只支持全量替换，不做合并。** 合并两套打卡记录会破坏唯一键与余额守恒，且单设备场景下几乎用不到。

### 6.4 提醒用户备份

设置页显示「上次备份时间」；超过 14 天在首页显示一条**轻提示**（不是通知，不是弹窗）。

## 7. 出第一个 apk（完整步骤）

**这是整个项目风险最高的一步，建议在写任何业务代码之前先跑通。**

### 7.1 前置条件

- Node 已装（本机 v24.16 ✅）
- Git 已装（本机 2.54 ✅）
- 一个免费 Expo 账号（在 https://expo.dev 注册）
- **不需要** Java、Android Studio、Android SDK、Google 账号、信用卡

### 7.2 步骤

**第 1 步：创建项目**

```bash
cd /c/Users/16907/Ember
npx create-expo-app@latest . --template default
```

> 如果目录非空会报错。可以先在临时目录创建，再把文件移过来；或先提交现有文档再执行。

**第 2 步：清空示例代码**

```bash
npm run reset-project
```

**第 3 步：手机预览**

```bash
npx expo start
```

手机装 **Expo Go**，扫描终端里的二维码。

- ✅ 成功标志：手机上看到默认页面，改一行文字后热重载生效
- ❌ 失败常见原因：手机与电脑不在同一 WiFi；公司网络隔离；Expo Go 版本与 SDK 不匹配

**第 4 步：安装 EAS CLI**

```bash
npm install -g eas-cli
eas login          # 用 Expo 账号登录
```

**第 5 步：配置构建**

```bash
eas build:configure
```

会生成 `eas.json`，并让你填 Android 包名，例如 `com.yourname.ember`。

> **包名是永久的。** 一旦发出去给朋友装过，改包名意味着他们必须卸载重装、本地数据全丢。想清楚再填。

**第 6 步：加 preview 配置**

编辑 `eas.json`，确保有这一段：

```json
{
  "build": {
    "preview": {
      "distribution": "internal",
      "android": {
        "buildType": "apk"
      }
    },
    "production": {}
  }
}
```

- `distribution: "internal"` → 生成可直接安装的包，不发布到商店
- `buildType: "apk"` → 生成 apk（默认是 aab，只能上商店）

**第 7 步：构建**

```bash
eas build -p android --profile preview
```

第一次会问是否生成 keystore，**选是**（EAS 自动生成并托管）。

**第 8 步：安装到手机**

构建完成后，网页会给一个二维码或链接。**用手机浏览器直接打开下载**，允许「未知来源」安装。

不需要数据线，不需要 adb。

**第 9 步：备份 keystore**

```bash
eas credentials -p android
```

把 keystore 下载下来，**密码存进密码管理器，并离线备份一份**。

> **keystore 丢了 = 老用户必须卸载重装 = 本地数据全没。** 这是不可恢复的。

### 7.3 时间与额度

| 项 | 数值 |
| --- | --- |
| 构建耗时 | 10–20 分钟（首次可能 30+） |
| 排队 | 免费档 0–30 分钟 |
| 端到端预期 | **20–60 分钟** |
| 免费额度 | 每月约 15 次 Android 构建 |
| 失败是否计数 | 通常计数（3 分钟内快速失败、每月前 10 次有豁免） |

**额度够用**，前提是：日常用 Expo Go 预览，只在「要发给手机」或「要验证原生行为」时才构建。

### 7.4 构建失败的排查顺序

按这个顺序查，**不要连续重试超过 2 次**（会烧光额度）。

1. **看 EAS 网页的分阶段日志，找第一个 error，不是最后一个。**
2. `npx expo-doctor` — 检查依赖版本是否匹配。
3. `npx expo export` — 本地验证 JS 能否打包（不需要 Android SDK）。
4. **Windows 大小写问题**：Windows 不区分大小写，Linux 构建机区分。`import './Components/Card'` 在本地能跑，云端找不到。检查所有 import 路径的大小写与文件名完全一致。
5. 回退到上一个能构建成功的 commit，二分定位。
6. 用空白模板构建一次，区分「环境问题」还是「你的代码问题」。
7. 搜英文错误原文 + SDK 版本号。

### 7.5 常见失败原因

| 原因 | 表现 | 解决 |
| --- | --- | --- |
| 用了 `npm install` 装原生库 | 版本不匹配，构建或运行时崩溃 | 一律用 `npx expo install` |
| `app.json` 图标路径错 | 构建早期失败 | 检查文件是否存在、扩展名是否对 |
| 需要 config plugin 的库没配 | 原生模块缺失 | 看该库文档，加到 `app.json` 的 `plugins` |
| Windows 大小写 | Linux 找不到文件 | 统一路径大小写 |
| lockfile 与 package.json 不一致 | 依赖安装失败 | 删 `node_modules` + `package-lock.json` 重装 |
| npm 网络超时 | 下载失败 | 换镜像源；重试 |

### 7.6 侧载安装的注意事项

| 项 | 说明 |
| --- | --- |
| 允许未知来源 | 系统设置 → 安全 → 允许安装未知应用 → 选择浏览器/文件管理器 |
| Play Protect 警告 | 会弹「不安全应用」，选「仍然安装」 |
| 国产 ROM 扫描 | 小米/华为会扫描一遍，等几秒 |
| 签名必须一致 | 升级时必须用同一个 keystore，否则必须先卸载 |
| versionCode 不能降 | 新版必须 ≥ 旧版 |
| 包体积 | universal apk 通常 60MB 上下 |

## 8. 发布：静态落地页

### 8.1 方案

一个单页静态网站，提供：

1. 一句话介绍 + 3 张截图
2. **下载 apk 按钮**
3. **安装步骤说明**（这是转化漏斗最陡的一段，必须写清楚）
4. 隐私说明（无网络权限、数据只在本地）
5. 版本更新记录

### 8.2 免费托管选项

| 方案 | 优点 | 缺点 |
| --- | --- | --- |
| **GitHub Pages** | 免费、稳定、与代码同仓库 | 国内访问偶尔慢 |
| **Cloudflare Pages** | 免费、国内访问相对快、可绑域名 | 需要注册 Cloudflare |
| **Netlify** | 免费、部署简单 | 国内访问一般 |

**推荐 Cloudflare Pages**：国内访问速度相对好，且免费额度充足。

### 8.3 apk 放哪里

| 方案 | 说明 |
| --- | --- |
| 同仓库的 `releases/` 目录 | 简单，但仓库会变大 |
| **GitHub Releases** | 推荐。每个版本一个文件，有版本号与下载计数 |
| Cloudflare R2 / 对象存储 | 需要额外配置 |

**推荐 GitHub Releases**：`eas build` 完成后下载 apk，手动上传到 Releases，落地页链接指向最新 release。

## 9. 依赖风险清单

| 依赖 | 风险 | 说明 | 应对 |
| --- | --- | --- | --- |
| **expo SDK** | **高** | 2026 年发了 55/56/57/58 四个大版本，每次都有 breaking change | 锁死版本，**一年只升一次**，选在新版本发布后 2–3 个月的稳定期 |
| react-native | 中 | 随 SDK 走 | 永远不单独升级 |
| expo-sqlite | 低 | 官方模块 | 保留 |
| reanimated + worklets | 中 | 版本必须严格配对，错位会白屏 | 用 `npx expo install` 自动对齐 |
| react-native-svg | 低 | 稳定 | 保留 |
| expo-notifications | 中高 | 平台限制 + OEM 后台管控 | 设计成增强，不依赖 |
| expo-file-system | 中 | SDK 54 起换新 API，旧函数移到 `/legacy` | 用新 API，别照旧教程 |
| eas build | 中 | 免费额度、产物约 30 天过期 | 每次构建后立即下载 apk 存档 |

### 两个元风险（比上面任何一条都重要）

**1. AI 的训练数据是滞后的。**
它会自信地写出旧版 API（比如已经废弃的 `FileSystem.documentDirectory`、旧版 Drizzle 配置）。你无法分辨。

对策：
- 永远用 `npx expo install`，不用 `npm install`
- 让 AI 改代码时，把「Expo SDK 58」和对应文档链接贴进上下文
- 报错先怀疑 API 过时

**2. 版本耦合是隐形炸弹。**
`reanimated ↔ worklets`、`expo ↔ react-native`，只要有一对错位，症状都是「能装、能开、然后白屏」。

这就是为什么依赖越少越好。

## 10. 维护成本控制

一个人维护 App 的真实负担不是写代码，是**每年 3–4 次 Expo 大版本 + 依赖缓慢腐烂**。

| 做法 | 说明 |
| --- | --- |
| 锁精确版本 | `package.json` 不写 `^`，提交 lockfile |
| 一年只升一次 SDK | 预留一个周末，选稳定期 |
| 不引入需要自定义原生代码的库 | 每少一个，升级时少一个雷 |
| 数据层只有一个文件 + 一个迁移器 | schema 变更只加列，不删不改 |
| 日期逻辑集中 + 单元测试 | 唯一值得写测试的地方 |
| 每个可用版本打 git tag + 存 apk | EAS 产物 30 天过期，别把唯一副本留在云上 |
| keystore 离线备份 | 丢了不可恢复 |
| 维护一页 `DECISIONS.md` | SDK 版本、包名、keystore 位置、构建命令、为什么砍了 X |
| 不做 Web 版 | 同时维护两套是双倍成本 |

## 11. 降级与体面收场

按损失从小到大：

| 降级 | 说明 |
| --- | --- |
| 1. 砍动画 | 只留淡入淡出和触感。视觉降级，可用性不降 |
| 2. 砍通知 | 改成「打开即用 + 每日补签」。很多成功的习惯 App 就是这样活的 |
| 3. 砍目标与回忆 | 只保留「今天」与「我的」两个 tab：打卡、等级、五维、余烬、连胜。已记录的数据不丢，只是不再有规划和回顾 |
| 4. 停更但继续自用 | 完全体面的结局。一个只服务自己的 apk 是成功，不是失败 |
| 5. 开源 | 当作作品集。但开源不等于有人接手，issue/PR 是新的负担 |
| 6. 彻底放弃 | **先把数据导出成 JSON。** 所以导出功能必须从第一版就有 |
